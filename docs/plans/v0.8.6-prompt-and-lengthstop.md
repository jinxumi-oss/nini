# v0.8.6 — Wire up tool system-prompt + length-stop safety

> **背景**：v0.8.5 修了 TUI 卡死 + 并行读之后，对 Pi v0.85.1 源码做了一次深度调研
> （`docs/research/pi-architecture.md`）。调研发现两个**隐藏多年的 bug**：
> 1. 工具的 `system_prompt_contribution()` 从 v0.7.1 起就在每个 tool 里实现了，
>    `nini-core::build_system_prompt_with_contributions()` 也有，但 **CLI/TUI 从未调用过**。
>    system prompt 一直是硬编码 "Available tools: bash, read, write, edit, grep, find"。
>    补：该函数收集时还有个 HashMap随机顺序的隐患，一起修。
> 2. LLM 因 `output_tokens` 上限被截断（`stop_reason: "length"`）时，
>    末尾的 tool_call JSON 可能被砍掉一半，nini 会把它当合法 JSON parse 后
>    用空参数执行工具。Pi 的处理是整批拒绝。

> **修订 v2（2026-09-30）**：9 个漏洞全部修复。
> - **PR 1**：补 `write` 工具缺失的 `system_prompt_contribution()`（漏洞1）；ToolRegistry 改为按名字排序输出（漏洞2）
> - **PR 2**：在 auto-compact-on-length-stop 之后才拒绝 tool_calls（漏洞3）；去掉重复 `AgentEvent::TurnEnd` yield（漏洞4）；不再需要 `is_valid_tool_call_json`（漏洞5）；测试 stub 改用合法 JSON（漏洞7）
> - **PR 3**：用 `s.base_dir.join("SKILL.md")` 代替不存在的 `s.file_path`（漏洞6）
> - **测试模块**（漏洞8）：改在 `tool_registry` 模块内加测试，避免 prompt_setup 反向依赖
> - 加 CHANGELOG 条目（漏洞9）

> **作者**：基于 `docs/research/pi-architecture.md` §3 列出的 P0 项
> **修订**：2026-09-30 (v2, audit fix)
> **基于**：v0.8.5 (commit `3bf4815`)

## 1. PR 1 — `fix(cli): wire up build_system_prompt_with_contributions`

### 1.1 问题

`crates/nini-core/src/tool.rs:431` 有现成的 `build_system_prompt_with_contributions()`，但有 3 个子问题要一起修：

**子问题 1 — 6 个工具里只有 5 个实现了 `system_prompt_contribution()`**（漏洞 1）：
- bash, read, edit, find, grep ✓
- **write ✗** — 如果直接调用 `build_system_prompt_with_contributions`，write 会被静默排除在 snippets 列表之外，model 仍读不到。

**子问题 2 — `ToolRegistry::tools()` 基于 HashMap iteration**（漏洞 2）：
```rust
pub fn tools(&self) -> impl Iterator<Item = Arc<dyn Tool>> + '_ {
    self.tools.values().cloned()  // HashMap 随机顺序
}
```
`build_system_prompt_with_contributions` 的输出顺序 = HashMap iteration → 每次跑顺序不同，测试不幂等，LLM token cache 命中率低。

**子问题 3 — CLI 用了硬编码字符串**（漏洞 5）：
`crates/nini-cli/src/prompt_setup.rs:46`：
```rust
s.push_str(
    "\nAvailable tools: bash, read, write, edit, grep, find. \
     Use them to complete complex multi-step tasks.",
);
```
即使是写出的 `write`，描述也是 Pi 用反了的固定一句话，不是用户查得到的一行 snippet。

### 1.2 修复（3 步）

#### 步骤 A — 补 `write` 工具的 `system_prompt_contribution()`（漏洞 1）

`crates/nini-tools/src/write.rs`：


#### 步骤 B — 排序输出（漏洞 2）

在 `build_system_prompt_with_contributions` 末尾排序：


改 `settings_to_system_prompt` 签名为接收 `&ToolRegistry`：

## 2. PR 2 — `fix(core): reject tool_calls on length stop`

### 2.1 问题（含 3 个子问题）

**子问题 A — 与现有 auto-compact-on-length-stop 冲突**（漏洞 3）：

`crates/nini-core/src/agent.rs:879-900` 已有：
```rust
let recoverable = crate::overflow::is_recoverable_length(
    &stop_reason, usage.output_tokens, config.max_tokens.unwrap_or(0),
);
// 上面返回 true 当 stop_reason == "length" 且没真正耗尽 output_tokens
if recoverable && crate::compaction::should_compact(...) {
    let _out = self.compact_history(summary_fn);
    yield AgentEvent::Error { message: format!("auto-compaction (overflow): ...") };
}
// 然后 fall through，不 continue，不 break
// → 如果 tool_calls 存在，进入 FuturesUnordered 执行
```

→ length stop 当前行为是 "compact → 推一个 error event → fall through"。PR 2 没说清楚与 auto-compact 的关系。

**子问题 B — 现有代码缺少 length-stop tool_call 安全门**（主目标）：

当 `stop_reason == "length"` 且有 `tool_calls`：
- LLM 输出 JSON 可能被砍掉一半（e.g. `{"command": "very long incomple`）
- `serde_json::from_str(&tc.input_json)` 返回 `Value::Null`
- 工具被调用，参数 = null
- 工具内部 `serde_json::from_value::<MyArgs>(null)` 失败 → ToolError::InvalidArgs
- 用户看到莫名的 "tool error: invalid args" 错误

Pi 的处理（`agent-loop.js:128`）：
```javascript
const executedToolBatch = message.stopReason === "length"
    ? await failToolCallsFromTruncatedMessage(toolCalls, emit)
    : await executeToolCalls(...);
```

**子问题 C — TurnEnd 不能 yield 第二次**（漏洞 4）：
原 PR 2 代码在 reject 分支又 yield 一次 `AgentEvent::TurnEnd`，但 `TurnEnd` 在更早的代码已经 yield 过。重复 yield 会让 TUI 的 phase state machine 出问题（虽然 v0.8.4 修了重复 PhaseChanged，但 TurnEnd 是 1:1 设计）。
### 2.2 修复（与 auto-compact 协调 + 无 TurnEnd 重复 + 删未定义 helper）

**位置**：`crates/nini-core/src/agent.rs` 中 `tool_calls` 填完之后、`yield AgentEvent::TurnEnd` 之前。

**策略（漏洞 3 修复）**：选定 **方案 A**（Pi 兼容）：
- `recoverable && should_compact` 仍然触发 auto-compaction（这是**好**的，因为它给 LLM 第二次机会）
- auto-compact 完**继续往下走**进入 turn 结束逻辑
- 如果 tool_calls 不为空 **且** stop_reason == "length"，**整批 reject + 跳过 FuturesUnordered**

这样比 "compact + 仍执行损坏的 tool" 安全，比 "compact + 不 reject" 噪音小。

**修复代码**：

```rust
// ... existing assistant message push ...

yield AgentEvent::TurnEnd { stop_reason: stop_reason.clone(), usage: last_usage };

// v0.8.6: length-stop 安全门（漏洞 3 修复：与 auto-compact 协作）
// 流程：
//   1. stop_reason == "length" 触发上面已有的 compact_history
//   2. 但 tool_calls JSON 可能被截断一半（max_tokens 上限）
//   3. 整批 reject，让 LLM 在下一轮用更短的 prompt 重新规划
//
// 注意：漏洞 4 修复 — TurnEnd 已经 yield 过，这里不再 yield。
// 注意：漏洞 5 修复 — 不需要 is_valid_tool_call_json helper。
if stop_reason == "length" && !tool_calls.is_empty() {
    let mut tool_results: Vec<ContentBlock> = Vec::with_capacity(tool_calls.len());
    for tc in &tool_calls {
        let reject_output = ToolOutput::err(
            "[reject] tool call arguments truncated by output token limit (length stop). \
             The LLM hit max_tokens before serializing the tool call JSON. \
             Retry with a shorter prompt or split the request."
                .to_string(),
        );
        yield AgentEvent::ToolResult {
            id: tc.id.clone(),
            output: reject_output.clone(),
        };
        tool_results.push(ContentBlock::ToolResult {
            tool_use_id: tc.id.clone(),
            content: reject_output.content,
            is_error: true,
        });
    }
    self.messages.push(Message {
        role: Role::Tool,
        content: tool_results,
        timestamp: 0,
    });
    // ★ 关键：跳过 v0.8.5 FuturesUnordered 块 ★
    // 跳到 turn 末尾，让 LLM 下一轮重新发 tool_calls
} else if !tool_calls.is_empty() {
    // 正常路径：v0.8.5 FuturesUnordered（不变）
    // ... existing parallel execution block ...
}

// 后续 steering hook 也不变（不管 length stop 走哪条路径，都要执行）
```

为什么**不需要** `is_valid_tool_call_json` helper（漏洞 5）：
- "length stop 时拒绝" 的逻辑应该**只看 stop_reason**，与 JSON 是否真损坏无关
- 保守 = 安全：宁可误杀不可漏杀
- 去掉这个 helper 少 5 LOC

## 3. PR 3 — `enhance(skills): include file location in prompt`

### 3.1 问题

`crates/nini-core/src/skills.rs:166` 当前输出：
```
The following skills provide specialized instructions for specific tasks.
Use the read tool to load a skill's file when the task matches its description.
When a skill file references a relative path, resolve it against the skill directory.

- beautiful-article: 把用户提供的素材...
- firecrawl: Search, scrape, and interact...
```

Pi (`skills/skills.ts:355`) 输出：
```
The following skills provide specialized instructions for specific tasks.
Use the read tool to load a skill's file when the task matches its description.
When a skill file references a relative path, resolve it against the skill directory (parent of SKILL.md / dirname of the path) and use that absolute path in tool commands.

<available_skills>
  <skill>
    <name>beautiful-article</name>
    <description>把用户提供的素材...</description>
    <location>/home/jin/.pi/agent/skills/beautiful-article/SKILL.md</location>
  </skill>
  <skill>
    <name>firecrawl</name>
    ...
    <location>/home/jin/.pi/agent/skills/firecrawl/SKILL.md</location>
  </skill>
</available_skills>
```

**差距**：nini 的模型知道 skill 的 name + description，但**不知道文件路径**，所以无法用 `read` 实际加载 skill 内容。skill 永远不会被触发。

### 3.2 修复（漏洞 6：s.file_path 字段不存在）

**关键**：`Skill` struct **没有 `file_path` 字段**，只有 `base_dir: PathBuf`（目录）。
skill 文件约定是 `base_dir/SKILL.md`（看 `skills.rs::load_skill` 加载路径）。

```rust
// crates/nini-core/src/skills.rs::format_skills_for_prompt
pub fn format_skills_for_prompt(skills: &[Skill]) -> String {
    let visible: Vec<&Skill> = skills.iter().filter(|s| !s.disable_model_invocation).collect();
    if visible.is_empty() {
        return String::new();
    }
    let mut out = String::from(
        "\n\nThe following skills provide specialized instructions for specific tasks.\n\
         Use the read tool to load a skill's file when the task matches its description.\n\
         When a skill file references a relative path, resolve it against the skill directory.\n\
         \n\
         <available_skills>\n",
    );
    for s in visible {
        // v0.8.6: 漏洞 6 修复——s 没有 file_path 字段，用 base_dir + SKILL.md
        let skill_path = s.base_dir.join("SKILL.md");
        out.push_str(&format!(
            "  <skill>\n    <name>{}</name>\n    <description>{}</description>\n    <location>{}</location>\n  </skill>\n",
            xml_escape(&s.name),
            xml_escape(&s.description),
            xml_escape(&skill_path.display().to_string()),
        ));
    }
    out.push_str("</available_skills>\n");
    out
}

fn xml_escape(s: &str) -> String {
    s.replace('&', "&").replace('<', "<").replace('>', ">").replace('"', """)
}
```

如果以后 skill 文件名需要可配置，可以给 `Skill` 加 `file_path: PathBuf` 字段并在 `load_skill` 时填——但这是另外的 PR，不是本计划范围。
