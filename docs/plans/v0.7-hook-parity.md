# nini v0.7 — Hook Parity Plan

> 目标：把 nini 的 agent loop 改造为 Pi-兼容的钩子架构，**主路径精简，所有可扩展能力通过 trait 钩子暴露**。

**Last updated:** 2026-09-23
**Version:** 2 (post-review, fixed 14 issues)
**Target release:** nini v0.7.0

---

## 背景

`docs/spec-v0.85.1`（来自 wiki 的 Pi Agent Loop 架构提炼）描述了 9 个钩子 + 4 阶段工具生命周期 + 7 变体消息 + 2 种执行模式 + 2 个交互队列 + 3 种上下文机制。

当前 nini v0.6.1 实现度约 60%：核心机制都有，但**全部写死在 `crates/nini-core/src/agent.rs` 里**，没有暴露钩子接口。

> Pi 设计哲学："主路径极简单 + 钩子接口丰富"
> nini 现状："主路径不极简，钩子几乎没有"

## 范围

### In scope（v0.7.0）

- **M1** — Steering / Follow-up 消息队列（mid-run 注入；不复用 `pending_next_turn_messages`）
- **M2** — Tool lifecycle 钩子（before/after/prepare/finalize；Option<Box<dyn ...>> 模型；Allow/Deny 二态）
- **M3a** — 消息变体（Notification / UiMessage / AppMessage + JSONL v4 兼容 + convert_to_llm 默认过滤）
- **M3b** — Context 钩子（convert_to_llm / transform_context / shouldStopAfterTurn；max_iterations 保留为硬安全网）
- **M5b** — Operations trait（BashOperations / ReadOperations；BashRunner 跨 crate 迁移到 nini-tools）

### Out of scope（v0.8+）

- Parallel tool execution（M4）— 文件依赖图方案还没设计
- TrustStore "Ask" 决策（带 TUI 用户确认）— 需要跨任务异步信号
- C ABI 扩展桥接 — nini-ext v0.7 仍只支持进程内 Rust 扩展
- v0.6.x 已发的 ExternalEditor / CommandPalette / TranscriptSearch 改键位

## 主路径改造目标

**Before（v0.6.1，`agent.rs` 第 619–952 行，333 行）**：

```rust
loop {
    if abort.is_aborted() { ... }
    if should_compact(...) { /* hardcode 触发 */ }
    let request = build_request(...);  // 硬编码
    let mut stream = provider.stream(request);
    // 流式处理 + 工具执行（hardcode 2 阶段）
    for tc in &tool_calls {
        t.execute(args, ctx).await;
        push ToolResult;
    }
    self.messages.push(tool_result_msg);
}
```

**After（v0.7.0，目标 ≤ 100 行）**：

```rust
loop {
    if self.host.should_stop_after_turn(&self.messages) { break; }
    if abort.is_aborted() { break; }
    let ctx_msgs = self.host.transform_context(&self.messages);
    let llm_msgs = self.host.convert_to_llm(&ctx_msgs);
    let request = build_request(&config, &llm_msgs, &tools);
    let (text, tool_calls) = stream_and_collect(request).await;
    if tool_calls.is_empty() { break; }
    let outputs = self.execute_tools(tool_calls).await;
    let steering = self.host.get_steering_messages(&outputs);
    self.append_turn(outputs, steering);
    let followup = self.host.get_followup_messages(&self.messages);
    self.append_followup(followup);
}
```

主路径从 333 行 → 80 行，逻辑搬到 `execute_tools()` / `append_turn()` 等命名函数，每个都是单测可覆盖的纯逻辑。

## 里程碑

### M1 — Steering / Follow-up 消息队列

**为什么先做**：人机协作的核心能力，Pi 用户最常提的差异化特性。改造窗口小，收益大。

**NOT**：复用 `pending_next_turn_messages` —— 那是 TUI 层的 pre-prompt 队列，语义和 Pi 的 mid-run 注入**完全不同**。

**交付**：

| 改动 | 文件 | 详情 |
|---|---|---|
| 新 trait `AgentLoopHooks`（在 `nini-core`） | `crates/nini-core/src/agent_hooks.rs`（新建） | 默认 impl 全是空 Vec |
| `get_steering_messages(&self, &[Message]) -> Vec<Message>` | 同上 | "工具执行完后、下轮 LLM 调用前"注入 |
| `get_followup_messages(&self, &[Message]) -> Vec<Message>` | 同上 | "agent 收尾前"注入 |
| `Agent` 加 `pub hooks: Arc<dyn AgentLoopHooks>` 字段 | `crates/nini-core/src/agent.rs` | 默认 `Arc::new(NoopHooks)` |
| `Agent::run` 主循环插入钩子调用 | 同上 | 见下方"注入时机" |
| `NoopHooks` 默认实现 | `crates/nini-core/src/agent_hooks.rs` | 全空，全 panic-safe |
| `panic::catch_unwind` 包裹钩子调用（防御性） | 同上 | 钩子抛错 → 返回空 Vec + log warn |

**注入时机（精确到代码位置）**：

```
Agent::run 主循环：
  1. 调模型前      → [M3b] transform_context + convert_to_llm
  2. 流式收完     → if tool_calls.is_empty() break
  3. 工具执行完   → 收集 ToolResult 进 messages
  4. ★ 此时调用 host.get_steering_messages(&recent_turn)
                    → 把返回的 Message 追加到 self.messages
                    → 然后继续下一轮（LLM 会看到）
  5. 下一轮调模型  → 看到 steering 注入的消息
  6. 模型最终收尾 → if tool_calls.is_empty() break
  7. ★ 此时调用 host.get_followup_messages(&self.messages)
                    → 把返回的 Message 追加到 self.messages
                    → 然后退出循环
```

**测试**（净增 12 + 3 = 15）：

行为测试：
- 默认 NoopHooks → 行为与 v0.6.1 完全一致（regression）
- 自定义 hooks 返回 1 条 steering → 出现在下一轮 LLM 请求的 messages 里
- 自定义 hooks 返回 1 条 followup → 出现在 agent 退出前的 messages 里
- steering 和 followup 都返回空 → 行为不变（idempotent）
- 自定义 hooks 返回 3 条 steering → 全部追加，不去重
- 钩子在第二轮回被调用 → 每次工具执行完都能注入

契约测试：
- 钩子闭包 `panic!()` → 主路径不崩，返回空 Vec + log warn
- 钩子无限递归调 agent.run → 检测循环（实现层防御）
- 钩子返回的 Message role = System → 仍按预期进 LLM 请求

**估计时间**：1 个 session。

### M2 — Tool lifecycle 钩子

**为什么做**：Pi 安全模型的基石是 Before/AfterToolCall。当前 nini 的 `ProjectTrustStore` 只读（`get(&cwd)`），无法"调用前问、调用后改"。

**交付**：

| 改动 | 文件 | 详情 |
|---|---|---|
| 新 trait `BeforeExecute`（`async fn run(&self, args, ctx) -> Result<Option<Value>, ToolError>`） | `crates/nini-core/src/tool.rs` | 默认 impl = identity |
| 新 trait `AfterExecute`（`async fn run(&self, output, ctx) -> Result<ToolOutput, ToolError>`） | 同上 | 默认 impl = identity |
| `Tool` trait 加 `fn before(&self) -> Option<Box<dyn BeforeExecute>>` 默认 `None` | 同上 | 现有工具无破坏 |
| `Tool` trait 加 `fn after(&self) -> Option<Box<dyn AfterExecute>>` 默认 `None` | 同上 | 同上 |
| `Agent::execute_tools()` 拆 4 阶段 | `crates/nini-core/src/agent.rs` | before → execute → after → emit |
| `WrappedTool` newtype（实现 Tool trait） | `crates/nini-core/src/tool.rs` | 委托 inner + 调 before/after |
| `ProjectTrustStore::check(tool, args) -> TrustDecision` 二态 | `crates/nini-core/src/project_trust.rs` | `Allow` / `Deny`（Ask 推 v0.8） |
| 现有 `BashRunner` 加 `before()` 返回路径白名单检查 | `crates/nini-tui/src/bash_runner.rs` | TrustStore::Deny → 路径不在白名单则拒 |

**测试**（净增 20 + 5 = 25）：

行为测试：
- 默认 `before() = None` → 行为不变（regression）
- before 返回 `Some(modified_args)` → tool 收到修改后 args
- after 改写 `ToolOutput.content` → LLM 看到脱敏内容
- WrappedTool 包 Read，before 注入告警 → LLM 看到
- TrustStore::Deny + bash tool → 工具不跑，ToolResult.is_error = true
- TrustStore::Allow + bash tool → 正常跑

契约测试：
- before 抛 panic → PermissionDenied，ToolResult.is_error = true
- after 抛 panic → 输出原 ToolOutput + log warn
- before 返回 `Err` → ToolResult.is_error = true，error message 包含原因

回归测试：
- 580 个旧测试全绿（最大承诺）

**估计时间**：1 个 session。

### M3b — Context 钩子

**为什么做**："上下文是硬约束"哲学的体现。把 hardcode 的 compaction / iteration 限改成可注入。

**交付**：

| 改动 | 文件 | 详情 |
|---|---|---|
| `AgentLoopHooks` trait 加 3 个方法 | `crates/nini-core/src/agent_hooks.rs` | `convert_to_llm` / `transform_context` / `should_stop_after_turn` |
| `TransformResult { messages, dropped_count, reason }` 结构体 | 同上 | 替代裸 `Vec<Message>` |
| `NoopHooks` 默认实现更新 | 同上 | identity / 不丢消息 / 不停 |
| `Agent::run` 主循环 5 步改写为 M3b 钩子版本 | `crates/nini-core/src/agent.rs` | 见下方"主路径" |
| `compact_history` / `should_compact` 调用挪到默认 `transform_context` 实现里 | `crates/nini-core/src/compaction.rs` | 默认 impl 保留当前行为 |
| `max_iterations` 保留为**硬安全网**，与 `should_stopAfterTurn` 并存 | `crates/nini-core/src/agent.rs` | 两者不互斥 |

**主路径 5 步详细**：

```rust
loop {
    // 1. 软停止信号（钩子能提前拦）
    if self.host.should_stop_after_turn(&self.messages) { break; }
    // 2. 硬安全网（保留 max_iterations）
    if iteration > config.max_iterations { break; }
    // 3. transform_context（钩子：注入、压缩、裁剪）
    let transformed = self.host.transform_context(&self.messages);
    // 4. convert_to_llm（钩子：过滤 Notification/UiMessage/AppMessage）
    let llm_msgs = self.host.convert_to_llm(&transformed.messages);
    // 5. 流式调模型
    let request = build_request(&config, &llm_msgs, &tools);
    let (text, tool_calls) = stream_and_collect(request).await;
    // 6. 退出条件
    if tool_calls.is_empty() {
        // ★ followup 注入（agent 收尾前）
        let followup = self.host.get_followup_messages(&self.messages);
        self.append_followup(followup);
        break;
    }
    // 7. 工具执行（4 阶段：before / execute / after / emit）
    let outputs = self.execute_tools(tool_calls).await;
    // 8. ★ steering 注入（工具执行后、下轮 LLM 调用前）
    let steering = self.host.get_steering_messages(&recent_turn);
    self.append_steering(steering);
    // loop 继续
}
```

**测试**（净增 15 + 3 = 18）：

行为测试：
- 默认 convert_to_llm = identity → 主路径行为不变
- 默认 convert_to_llm 过滤掉 Notification 变体 → LLM 看不到
- 自定义 convert_to_llm 在第 5 条消息后插 system 提示 → LLM 看到
- 自定义 transform_context 砍掉前 N 条 → 上下文缩短
- 默认 transform_context 仍触发 compaction（行为不变）
- 自定义 should_stop_after_turn 返回 true → agent 提前停
- max_iterations = 2，自定义 hook 不拦 → 仍受硬安全网限制
- max_iterations = 100，自定义 hook 拦 → 在 100 轮前就停

契约测试：
- transform_context 抛错 → 返回原 messages + log warn
- convert_to_llm 抛错 → 返回原 messages + log warn
- should_stop_after_turn 抛错 → 返回 false（继续跑）

回归测试：
- 595 个旧测试（v0.7-M1 + v0.7-M2 后）全绿

**估计时间**：1 个 session。

### M5b — Operations trait

**为什么做**：让工具的执行层（命令跑在哪、文件怎么读）可被远程化、mock 化、策略化。

**前置**：M2 已经把 `BashRunner` 的 cross-crate 问题暴露出来，需要同步迁移。

**交付**：

| 改动 | 文件 | 详情 |
|---|---|---|
| 新 trait `BashOperations`（`fn exec`、`fn which`、`fn kill_pg`） | `crates/nini-tools/src/bash.rs`（新建） | 默认 impl = 当前 std::process + setsid |
| 新 trait `ReadOperations`（`fn read`、`fn stat`） | `crates/nini-tools/src/read.rs`（新建） | 默认 impl = 当前 std::fs |
| `BashRunner` 从 `nini-tui/src/bash_runner.rs` **迁移**到 `nini-tools/src/bash_runner.rs` | 跨 crate | nini-tui 的 BashRunner 删掉 |
| `BashRunner` 实现 `BashOperations` | 同上 | 默认 impl |
| `nini-tools::bash` 工具委托给 `BashRunner` | `crates/nini-tools/src/bash.rs` | 工具 trait 用 runner |
| `nini-tools::read` 工具委托给 `ReadOperations` 默认实现 | `crates/nini-tools/src/read.rs` | 同上 |

**测试**（净增 8 + 2 = 10）：

行为测试：
- `BashOperations` mock 委托 → bash 工具走 mock
- `ReadOperations::read` 抛错 → 当前实现兜底，ToolResult.is_error = true
- BashRunner 跨 crate 迁移后所有现有 bash 测试 → 全绿（最大回归承诺）

契约测试：
- `BashOperations::kill_pg` 抛错 → 不崩，错误日志

**估计时间**：1 个 session。

## 钩子执行模型（统一约定）

```
- 所有钩子都是同步 fn（trait 方法）或 async fn（trait 方法）
- 钩子在 agent 主线程上调用（不并发、不在 tokio::spawn 里）
- 钩子可以 `await`，但必须能取消（响应 abort_signal）
- 钩子抛错 → 见各 M 的契约测试
- 钩子**禁止**调用 agent.run()（防止无限递归）
- 钩子**禁止**持有 &mut Agent（防止借用冲突）
```

| 风险 | 等级 | 缓解 |

## 独立可回退性

每个 M 单独 commit，commit 后 `cargo test --workspace` 全绿 → 都能独立 revert。

依赖关系：
- M1 不依赖任何 M
- M2 不依赖任何 M
- M3a 不依赖任何 M
- M3b 依赖 M3a（convert_to_llm 默认实现要识别新变体）
- M5b 不依赖任何 M（但 M2 的 before/after 钩子可能用到 BashOperations trait）

耦合点：
- M3b 必须在 M3a 之后（已说明）
- M5b 必须在 M2 之后（trust 检查可能要调用 BashOperations::which 检查路径）
