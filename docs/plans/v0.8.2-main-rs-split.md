## 二、目标架构

### 6 个模块 + 一个 slim main

```
crates/nini-cli/src/
  main.rs            ← ~50 LOC（仅 args 解析 + entry 派发）
  app.rs             ← App 工厂 + bootstrap
  provider_factory.rs ← build_provider() + make_anthropic() + parse_scripted_turns()
  tool_registry.rs   ← build_tools() + filter_tools()
  prompt_setup.rs    ← model_for_cfg() + settings_to_system_prompt()
  demo.rs            ← run_demo() + run_print() + demo_* fixtures + cli_entry_legacy()
  info.rs            ← run_info()
  startup_ui.rs      ← 已存在的 stub
```

### 模块职责

| 模块 | 公开 API |
|---|---|
| `app.rs` | `App::new(args) -> Result<App>` + `App::run_tui()` |
| `provider_factory.rs` | `build_provider(name, turns, keys, urls) -> Result<Arc<Provider>>` + `parse_scripted_turns(s) -> Vec<Vec<FixtureTurn>>` |
| `tool_registry.rs` | `build_tools() -> ToolRegistry` + `filter_tools(reg, cli, ...) -> ToolRegistry` |
| `prompt_setup.rs` | `model_for_cfg(&Settings) -> String` + `settings_to_system_prompt(&Settings, &str) -> String` |
| `demo.rs` | `run_demo(...)` + `run_print(...)` + 4 个 fixture builders |
| `info.rs` | `run_info() -> Result<()>` |
| `main.rs` | `#[tokio::main] async fn main()` — 30-50 LOC |

### 目标 LOC

| 模块 | 估算 |
|---|---|
| `main.rs` | ~50（入口派发） |

## 四、风险与缓解

### 风险 1：AgentDriver closure（220+ LOC）难以拆分

main.rs 内的 `agent_driver: AgentDriver = Arc::new(move |user_msg, sink, done| { ... })` 是一个巨大的闭包，包含 9 个 match arm 把 AgentEvent 转为 AgentEventLite。

**缓解**：保留在 `app.rs`（靠近调用方），不拆出独立模块。可以加 `// v0.8.2 note: this closure could be a method on a helper type` 注释。

### 风险 2：测试覆盖率上升导致 main.rs 仍有"死代码"

`pub fn` 提到独立模块后，`main.rs` 内调用语法变化（`prompt_setup::model_for_cfg(&settings)` vs `model_for_cfg(&settings)`）。所有 callers 必须更新。

**缓解**：编译器会强制更新（一次性 ~30 处）。

### 风险 3：模块可见性

新模块需要 `pub` 才能被 main.rs 引用。但 pub 暴露给整个 crate（不只是 main.rs）。

**缓解**：用 `pub(crate)` 而非 `pub`，限定可见性在 nini-cli 内。

### 风险 4：startup_ui.rs stub 已有，但从未实现

`needs_first_time_setup` 永远返回 false，`init_agent_dir` 永远返回 Ok。v0.8.2 不实现它（out of scope），但加 `#[allow(dead_code)]` 抑制警告。
