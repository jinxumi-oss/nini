## 3. R1 — agent loop 补 L1 外层（P0）

### 差距（已逐行核实）

| # | 差距 | nini 位置 | Pi 0.84.2 位置 |
|---|---|---|---|
| 1 | **只有一层循环** | `agent.rs:741` 单个 `loop {` | `agent-loop.js:85` 外层 + `:88` 内层 |
| 2 | **follow-up 塞进历史后 `return`**，不发起 LLM 调用 | `agent.rs:1179-1199` | `:163-167` poll follow-up → `continue` |
| 3 | steering 仅在工具分支被 poll | `agent.rs:1451-1456` | `:160` 每轮末尾**无条件** poll |
| 4 | `should_stop_after_turn` 在循环**开头** | `agent.rs:749-757` | `:151` turn_end 之后、poll 队列之前 |
| 5 | 无队列抽象、无 `steer()`/`followUp()`、TUI 无入口 | `grep steer/followUp` 零命中 | `agent.js:51,63,128,173,177` |

### 差距 2 的真实后果（比"少一层循环"严重）

nini 把 follow-up `push` 进 `self.messages` 然后返回。follow-up 因此从
**一个待执行的任务**降级为**一段死上下文** —— 下次用户打字时，模型看到的是
`[…历史…, followup消息, 新用户消息]`，会把它当背景资料而非任务。

Pi 的语义是它触发**一个全新 turn**。对模型行为影响是量级性的。

### 现有测试把错误行为固化了

```rust
// agent.rs:2668-2670
assert_eq!(hooks.followup_count(), 1, "followup fires once per run");
assert_eq!(agent.messages().len(), 4);   // "2 base + 2 followup"
```

只断言 hook 被调用 + 消息进了历史，**从不断言发生了第二次 LLM 调用**。用单轮响应 provider，
若循环真的执行，provider 会被调第二次、`messages().len()` 也会变 ⇒ **此测试在修复后必然失败**。
它锁定的正是"follow-up = 死上下文"。

`steering_hook_fires_only_after_tool_execution`（`:2693`）用**空队列**断言 `steering_count()==0`
—— 空队列在两侧都是 0，**测试名声称的不变量，测试体没验证**。

### 实施

1. `PendingMessageQueue`（`enqueue`/`drain(mode)`/`hasItems`/`clear`，支持 `one-at-a-time` 默认与 `all`）
2. `Agent::steer()` / `follow_up()` / `has_queued_messages()`；并发 `prompt()` 按 Pi `agent.js:228` 抛错
3. `run()` 改为两层；`tool_calls.is_empty()` 分支 `return` → `break`
4. steering poll 移到内层末尾无条件
5. `should_stop_after_turn` 移到 turn_end 之后
6. `max_iterations` 同时约束外层（否则 follow-up 可无限复活）
7. TUI 入口：运行时 `Enter`→steer，`Alt+Enter`→follow-up
8. **改写上述两个测试**，并新增"follow-up 触发第二次 LLM 调用"的断言

### 反向影响（必须提前决策）

`RunConfig` 目前在 `app.rs` 一次性构建后 `move` 进 driver 闭包。R1 完成后
`/reload`（P1-4，claims "Reload keybindings, extensions, skills, prompts, themes, and context files"，
Pi 7 项 / nini 只数 skills）若要真生效，需要 `RunConfig` 运行时可变。
**R1 与 `/reload` 改造会改写同一处代码，必须排在一起。**

## 4. R7 — session serde 对齐（P0，最小改动最大回报）

### 实测证据（本机 339 个真实 session）

```
READ OK: 339   FAILED: 0
entries total = 31151   skipped total = 28808      ← 48% 静默丢弃
```

单文件逐行解剖（8 行真实 session）：

| 行 | Pi 实际写 | nini 判定 |
|---|---|---|
| L1 `session` | `type,version,id,timestamp,cwd` | ✅ |
| L2 `model_change` | `modelId` | ✅ |
| L3 `thinking_level_change` | **`thinkingLevel`** | ❌ 丢 |
| L4 `message`/`user` | `role,content,timestamp` | ✅ |
| L5–L8 `message`/`assistant` | **`stopReason`, `errorMessage`** | ❌❌❌❌ 全丢 |

### 三处根因

| 根因 | 位置 | Pi 写法 | nini 写法 |
|---|---|---|---|
| `AssistantMessage.stop_reason` 缺 rename | `entries.rs` | `stopReason` | `stop_reason` |
| `AssistantMessage.error_message` 缺 rename | `entries.rs` | `errorMessage` | `error_message` |
| `ThinkingLevelChangeEntry.thinking_level` 缺 rename | `entries.rs:64` | `thinkingLevel` | `thinking_level` |
| 缺 `active_tools_change` entry 变体 | `SessionEntry` 枚举 | Pi `legacy-v3.ts:294` 有 | 无 |

**后果：nini 恢复一个 Pi 会话，只能看到用户说了什么，看不到模型答了什么**，而返回 `READ OK`。

### 实施

- 补 3 处 `#[serde(rename = "…")]`
- 补 `ActiveToolsChangeEntry` 变体
- **`Write` 方向**：用 Pi 0.84.2 的 `parseJsonlSessionHeader` + `normalizeLegacyV3Records`
  实测 nini 写出的文件能否读回（现在**零样本**）
- 兼容策略：读侧同时接受 camelCase 与 snake_case（Pi 0.84.2 写 camel，旧 nini 写 snake），
  写侧统一 camelCase

**注意**：nini `Line` 是 untagged，`SessionHeader.version` 必填，Pi 真实文件也有 —— header 层已验证兼容。

## 6. R2 — `nini-ai` 拆两层（P1，最大缺口）

### 现状 vs Pi

```
Pi pi-ai/src/                        nini-ai/src/
├── api/        353 节点 · 20 dialect   15 个平铺文件
├── providers/  177 节点 · ~37 品牌      （品牌 = 协议，混为一谈）
├── auth/       130 节点                无
└── utils/      104 节点                无
```

Pi 的 20 个线路协议：`anthropic-messages` `openai-responses` `openai-completions`
`bedrock-converse-stream` `google-generative-ai` `google-vertex` `mistral-conversations`
`openai-codex-responses` `azure-openai-responses` `constrained-sampling`
`transform-messages` `openai-prompt-cache` `cloudflare` `openrouter-images` `pi-messages` …

### 架构性后果

nini 里"加一个走 OpenAI 协议的新品牌" = 复制整个 provider 文件。
Pi 里 = 新增 `<brand>.models.ts` 复用已有 dialect。**边际成本差一个数量级。**

### 实施

1. `nini-ai/src/api/` —— 每个 dialect 一个模块，只负责 wire format（请求构造 / SSE 解析 / 事件映射）
2. `nini-ai/src/providers/` —— 每个品牌一个声明，复用 dialect + 携带 model 目录
3. 现有 9 个 provider 逐个归位；**保持行为不变**（由 W0 的 `provider_wire` oracle 保证）
4. `fixture` provider 归入 `api/` 之外（它不在线上）

**这是纯重构，不加功能。** 任何行为变化都是回归，由 `provider_wire` oracle 拦截。

## 8. R8 — TUI 冻结（一条不做事的决策）

`nini-tui` 已是 `pi-tui` 的 3.20x。本轮**冻结 TUI 新功能**，只接受 bug 修复。
理由：边际收益最低，而 `nini-ai` 只有 0.21x。

> 风险：冻结会被读成"放弃"。需要明确 —— 这是**排序**决策，不是质量判断。
> 现有 TUI 能力（3.20x 覆盖）不删、不降级，只是不再投入增量。

## 10. 通用工程纪律（从本轮教训固化）

| 纪律 | 依据 |
|---|---|
| **先建 oracle 再改实现** | 没有 oracle，测试只能证明 nini 一致于自己 |
| **每个新测试必须被证伪过** | 临时回退修复，确认测试变红；本轮已用此法抓出一个同义反复的假测试 |
| **不得以"测试全绿"为验收** | 937 绿测试下有 8 个假成功命令 |
| **不删未接线的 Pi 架构** | `nini-ext`/`branch_summary`/`operations` 是未完成的重构，删掉等于固化差距 |
| **断言必须取自被测函数** | 测试里自造的常量是同义反复，绿了也什么都没证明 |
| **版本基准单一** | 0.84.2 / 0.85.1 / fixture-v2 三者互不相符，必须锁一个 |

## 11. 本计划自身的已知局限

1. **节点数是代理指标**，不是功能等价度。`nini-tui` 3.20x 可能意味着更碎而非更好。
2. `nini-tui` 在拆解文档中被 `pi-tui` 与 `pi-coding-agent` 两次计入，比值需按单次口径重算。
3. `pi-coding-agent`（0.73x）**只知总量，未分解内部构成** —— 是第二大缺口却最不透明。
4. 全部结论基于 **0.84.2**；若目标改为 0.85.1，R2 的 dialect 清单需重取，W0 需重录 fixture。
5. R1 的工期估算依赖 `max_iterations` 外层语义的最终决策，尚未定。
6. **未验证 nini→Pi 写入方向**（`nini -p` 不落盘，至今零样本），W0 建成前该方向风险未知。

### 12.4 过程中两次自我纠错

**① 版本/格式问题三次互相矛盾的读法。**

## 14. R1 实施记录 —— **完成**（2026-10-05）

### 14.1 专家解法：塌缩，而非嵌套

上一轮失败的根因是**模仿了 Pi 的语法而不是语义**。Pi 写的是嵌套双循环
（`agent-loop.js:85` L1 / `:88` L2），我照抄成 `loop { loop { … } }`，
在一个 1500 行的 `try_stream!` 生成器体里做括号手术 —— 四次静默失败。

**两层其实可以塌缩成单循环 + 顶部守卫**，因为两层的唯一区别是"什么时候退出"：

```rust
pending = poll_steering();                       // Pi :83
loop {
    if !has_more_tool_calls && pending.is_empty() {   // ← L2 本该退出 ⇒ 交给 L1
        let fu = poll_followup();                     // Pi :163
        if fu.is_empty() { return; }
        pending = fu;
    }
    inject(pending); turn();                         // Pi :96,:106
    has_more = <turn 有工具调用>;
    pending = poll_steering();                       // Pi :160
}
```

零嵌套 ⇒ 零括号手术。等价性写在代码注释里，可逐行核对。

### 14.2 行为变化

| | v0.9.1 | v0.10 |
|---|---|---|
| follow-up | 塞进历史后 `return`（**死上下文**） | 触发**新 turn**，模型真的去做 |
| steering | 只在工具分支 poll | 每轮末尾**无条件** poll（Pi `:160`） |
| 空 turn | 直接 `return` | 只置 flag，由守卫决定是否继续 |
| 外层无界 | — | `max_follow_up_rounds`（默认 16）独立于 `max_iterations` |

### 14.3 四个必须改写的既有测试（它们固化的是错误行为）

| 测试 | 原来断言 | 为什么是错的 |
|---|---|---|
| `followup_hook_injects_messages_on_run_end` | `messages().len() == 4` | 新旧行为下**计数都是 4** —— 这正是缺陷能长期存活的原因。现改为断言**第二个 turn 发生了**（5 条消息 + 尾部 assistant） |
| `steering_hook_fires_only_after_tool_execution` | `steering_count() == 0` | 名字和断言都编码了"无工具 ⇒ 不 poll steering"，与 Pi `:160` 矛盾。改为断言每轮都 poll |
| `CountingHooks` | 每次返回同一列表 | 那是**永动机**不是队列。改为 drain-once（对齐 `agent.js:63-71`） |

### 14.4 oracle（4 条全绿）

### 14.5 过程中我自己犯的三个错（都已修）

## 16. G2 —— 文件修改竞态（2026-10-05）

### 16.1 为什么先做这个而不是 R2

R2（`nini-ai` 拆两层）是**规模**问题：节点数 0.21x。
G2 是**正确性**问题：会损坏用户代码。按影响排序应先做。

### 16.2 实测

`EditTool::execute` 是 read-modify-write。nini 用 `FuturesUnordered` + worker pool
并发跑一批工具调用（`max_parallel_tools`），对读是收益，对写是数据丢失。

本机 8 个并发 edit 打同一文件，修复前跑 5 次：

```
1/8 edits reported success; final file has 1/8 markers edited
3/8 edits reported success; final file has 2/8 markers edited
4/8 edits reported success; final file has 2/8 markers edited
```

**触发场景很普通**：模型在一个 turn 里对同一文件做两处替换（最常见的编辑模式）。

**比丢失更新更糟**：临时文件名是 `.{file}.nini-tmp.{pid}` —— **只含进程 PID**。
同进程内同文件的并发写全部落到**同一个临时路径**，并发 truncate+write 会交错，
文件可能被**写坏**，不只是陈旧。

### 16.3 修复（对齐 Pi `withFileMutationQueue`）

Pi 在 `pi-agent-core/src/harness/tools/file-mutation-queue.ts` 里按
**canonical path** 建 promise 链：`edit.ts` / `write.ts` 各自包裹自己的实现。
同文件串行，**不同文件仍并发**。

1. 新增 `nini-tools/src/mutation_queue.rs`
   - `with_file_mutation_queue(path, f)`：per-canonical-path `tokio::sync::Mutex`
   - 队列表用 `Weak` 存引用，最后一个持有者释放后自动清理（对齐 Pi 的 WeakMap）
   - `canonicalize` 失败（`write` 建新文件）时退回绝对路径，对齐 Pi 的 `not_found` 处理
2. `EditTool::execute` / `WriteTool::execute` 的**函数体**整体包进队列
   —— 放在工具里而不是 agent 里，保证对任何调用方都成立
3. 临时名加进程内单调计数器（`unique_temp_name`）

### 16.4 oracle（3 条）+ 证伪

| 注入 | 结果 |
|---|---|
| 去掉 `edit` 的队列包裹 | 🔴 `concurrent_edits_to_one_file_all_survive` 变红：`lost update: 7 of 8 edits vanished` |
| 不同文件被全局串行化 | ✅ 由 `different_files_still_execute_in_parallel` 守住（<400ms 阈值） |

**一条没能证伪，如实记录**：把临时名退回「只含 pid」，3 条 oracle **全部仍绿**。
原因是有了队列后同文件已串行，临时名冲突**不可能再发生**。
唯一临时名是**纵深防御**（例如工具 future 被取消后残留的临时文件），**不是**主修复，
且 oracle 证明不了它。这一点不宣称"已验证"。

### 16.5 我在这个测试里写的死锁

单元测试 `same_path_serialises_different_paths_do_not` 挂了 60 秒以上。原因：

```rust
*peak.lock().unwrap() = (*peak.lock().unwrap()).max(…);   // ← 同一把 std Mutex 嵌套加锁
```

`std::sync::Mutex` **不可重入**。改用 `AtomicUsize` + `fetch_max` 后解决；
顺带满足了「`MutexGuard` 跨 `.await` 不是 `Send`」的编译约束。

**测试代码也会有 bug，而且这类 bug 表现为"挂住"而不是"失败"** —— 不设超时就会一直卡。

**测试：971 → 977（+3 oracle +3 单元）。clippy 0，fmt 干净。**

## 17. R1c —— 工具批的 `executionMode` 与 `terminate`（2026-10-05）

Pi 循环还剩两个能力 nini 完全没有。两者都在同一处代码（`executeToolCalls`）。

### 17.1 Pi 语义（`agent-loop.ts` / `types.ts`）

```ts
// types.ts:402-408
/** "sequential": this tool must execute one at a time with other tool calls. */
executionMode?: ToolExecutionMode

// agent-loop.ts:418-426 —— 有一个 sequential，整批降级

// agent-loop.ts:582-584 —— every，不是 some
return finalizedCalls.length > 0 && finalizedCalls.every((f) => f.result.terminate === true);

// agent-loop.ts:216 —— 在批次返回之后才更新

3. 批内任一工具 sequential ⇒ `parallelism = 1`（复用现有 worker pool，不引第二套执行路径）

5. `terminate_flags` 必须在**展平为 `ContentBlock` 之前**收集 —— 展平会丢掉该标记
6. 在工具块**结束后**按 `should_terminate_tool_batch` 更新 `has_more_tool_calls`

### 17.3 oracle（7 条）+ 证伪

| 注入 | 结果 |
|---|---|
| `every` 改成 `some` | 🔴 2 条变红（`terminate_requires_every…`、`one_non_terminating…`） |
| 忽略 `batch_is_sequential` | 🔴 `one_sequential_tool_downgrades_the_whole_batch` 变红（peak 8） |

## 18. R1d —— `shouldStopAfterTurn` 的调用位置（2026-10-05）

### 18.1 先做契约面对账，而不是凭印象挑

把 Pi 的 `AgentLoopConfig`（`types.ts`）11 个字段逐条对 nini：

| Pi 字段 | nini | 状态 |
|---|---|---|
| `model` / `convertToLlm` / `transformContext` | 都有 | ✅ |
| `getSteeringMessages` / `getFollowUpMessages` | 都有 | ✅ R1 |
| `toolExecution` | `RunConfig.tool_execution` | ✅ R1c |

| **`shouldStopAfterTurn?`** | 有，**位置错** | ❌ 本轮 |

### 18.2 Pi 的每轮顺序（`agent-loop.ts:225-250`）

```
LLM → 工具执行 → emit(turn_end) → prepareNextTurn → shouldStopAfterTurn → poll steering
```

nini 把 hook 放在**循环顶部**（LLM 调用之前），把契约倒转了两点：
1. hook **永远看不到已完成的 turn**（"上下文快满了就停"的扩展会比 Pi 早停一轮）
2. 它的裁决针对的是一个**尚未发生的 turn**

### 18.3 实测

```

## 19. R1e —— `prepareNextTurn`：运行中切模型（2026-10-05）

### 19.1 先查 Pi 到底用它做什么，再决定做不做

我上一轮说"先查 Pi 怎么用 `prepareNextTurn` 再决定做不做"。查完的结论是：
**它不是抽象扩展点，是承载具体行为的机制。**

Pi 的 session 层（`agent-session.ts:534-554`, `_installAgentNextTurnRefresh`）只做一件事：

```ts
this.agent.prepareNextTurnWithContext = async (turn, signal) => ({
    context: { ...previousContext, systemPrompt: …, tools: … },
    model: this.agent.state.model,
    thinkingLevel: this.agent.state.thinkingLevel,
});
```

**每轮把 live 状态重新同步进循环。** 这就是"运行中改模型/思考等级/工具能生效"的机制。

### 19.2 nini 的缺口（实测）

- TUI 改的是 `state.model_state.model`（`runtime.rs:583`、`:1099`）
- 场景**可达**：`tokio::select!`（`runtime.rs:561`）在 agent 运行期间持续收键 ⇒ 可 Ctrl+L
- `Agent::run` 在入口 `clone` 一次 `RunConfig`（`agent.rs:748`），循环内复用

⇒ 用户运行中切模型，状态栏变了，**但每一轮请求仍发给旧模型**。

oracle 实测（4 轮）：

```
saw ["model-A", "model-A", "model-A", "model-A"]
left: ["stop"]  right: ["prepare", "stop"]      ← 顺序也反
```

### 19.3 范围：只做 model（专家纪律）

Pi 的 `AgentLoopTurnUpdate` 还有 `context` 和 `thinkingLevel`，**都没做，也不该做** ——
nini 没有读者：

| 字段 | 为什么不做 |
|---|---|
| `thinkingLevel` | nini 的 `Request` **根本没有 thinking/reasoning 字段**。`thinking_level` 只在 TUI 状态和 settings.json 里，**从未发给任何 provider**。加一个没人读的字段比不加更糟 —— 它看起来像实现了。已单列为 R1f |
| `context` | Pi 从常驻 session 重同步；nini 的 `Agent` 由 driver 闭包每次 run 新建，**没有 session 可重读** |

### 19.4 改动

1. `TurnUpdate { model: Option<String> }` + `AgentLoopHooks::prepare_next_turn()`（默认空）
2. 循环内 `config` 改为 `mut`；按 **Pi 的顺序**（`agent-loop.ts:236-245` 在 `:250` 之前）
   先 `prepare_next_turn` 应用 model，再 `should_stop_after_turn`
3. TUI 接线：`AgentSink::current_model()` + `app.rs` 的 `LiveConfigHooks`
   —— **否则这就是又一次"嫁接到空处"**

### 19.5 oracle（3 条）+ 独立证伪

| 注入 | 结果 |
|---|---|
| 不应用 model 更新 | 🔴 `a_model_change_reaches_the_next_provider_request` 变红，回到全 `model-A` |
| 把 `should_stop` 调到 `prepare` 之前 | 🔴 `prepare_next_turn_runs_before_should_stop_after_turn` 变红 |

两条性质**各自独立**被证伪，不是靠同一条测试。

### 19.6 又一条我写错的期望值

`a_model_change_reaches_the_next_provider_request` 最初让 hook 从**第 2 次**调用才返回新模型，
却断言 `seen[1] == "model-B"`。实得 `[A, A, B, B]`。

**是夹具错，不是代码错** —— 第 2 轮之后才做的决定，不可能影响第 2 轮。
改为"hook 始终返回新模型"，既更简单，也精确对应用户场景（turn 1 期间切模型，turn 2 生效）。

## 21. 可观察性审计（2026-10-05）

### 21.1 审计的两条轴

R1f 的教训是：**链上不可观察 ⇒ 测不到 ⇒ 静默消失**。据此审两条轴：

- **轴 A｜不可观察的产物生产者** —— 私有但**唯一**产出一个外部产物（wire body / 渲染帧 / 文件 / prompt）的函数
- **轴 B｜写入但零读取的字段** —— "记录了但没接线"的结构性签名

### 21.2 结果：审计推翻了三个假设（这正是审计的价值）

| 假设 | 结论 |
|---|---|
| "cache token 从未计入上下文" | ❌ **错**。`provider.rs:85-91` 的 `context_tokens_from_usage` 已含 `cache_read + cache_write`。真实缺口只剩"未优先采用 provider 的 `totalTokens`" |

**判定标准因此收紧为**：私有函数只有在它是某产物的**唯一**生产者时才是可观察性缺口。透传函数与被上层快照覆盖的函数都不是。

### 21.4 顺着 `first_kept_entry_id` 挖出的真缺陷（高影响）

`first_kept_entry_id` 零读取，追问"nini 靠什么恢复压缩后的历史"，发现**根本没有恢复**：

**后果**（三段判定）：

| 时机 | 结果 |
|---|---|
| 运行内 | ✅ 摘要在 context 里 |
| 落盘 | ❌ 前缀与摘要都没写进 session 文件 |

   - `session_entry_to_llm_message` 把 Compaction 条目转成 `[CONTEXT SUMMARY]` 上下文消息
   - oracle：`/resume` 一个含压缩的会话 ⇒ 摘要必须回到 transcript
2. **R2b（P1）** `first_kept_entry_id` 真正用于尾部校验（对齐 Pi 的 parent 链回溯）
3. **R2c（P2）** 其余 5 个零读取字段：逐个判定"接上"还是"删掉"，不留既不读也不写的中间态
4. **R3**（原计划）`operations.rs` 接线 —— 其余 5 个 Operations 接口 + 7 个品牌可 mock
5. **R4**（原计划）`nini-ai` 拆两层

### 22.4 推翻之三：门禁两头都漏（M0 的实证依据）

审查对 1176 个测试做了可信度抽查。发现**两类缺陷同时存在**：

**(a) 测试不接触生产代码，测试把 bug 写成了期望**

`openai.rs:85-86` 生产代码内联 URL 拼接；`openai.rs:977-1008` 的三个 URL 测试把同一段 `format!` **复制进测试体**独立计算，从不调用生产代码。其中 `handles_trailing_slash` 断言：

```rust
assert_eq!(url, "https://example.com/v1//v1/chat/completions");
// "This is a known minor quirk — users shouldn't add trailing slashes."
```

即：**测试断言了 bug，并且与生产代码没有连接**。

**(b) 零覆盖的地方存在真缺陷**

| dialect | URL 拼接 | 规则 | oracle |
|---|---|---|---|
| `openai.rs:85` | `{base}{/v1\|}/chat/completions` | 跳过重复 `/v1` | 测试是同义反复 |
| `anthropic.rs:73` | `{base}/v1/messages` | 无条件加 | **零** |
| `openai_responses.rs:69` | `{base}/v1/responses` | 无条件加 | **零** |

**查 Pi 源码后的修正（避免误报）**：后两条**不是 bug**。Pi 把 `baseURL: model.baseUrl` 交给官方 SDK，由 SDK 拼 `/v1/messages` —— 无条件加正是 Anthropic SDK 的行为。`openai.rs` 的 `ends_with("/v1")` 跳过逻辑则是对齐 OpenAI SDK，方向正确。

**唯一真 bug**：OpenAI SDK 用 URL 相对解析，对尾斜杠是健壮的；nini 是**手写模拟**该语义，尾斜杠输入下产出 `//v1`，与 SDK 不等价。而 `OPENAI_BASE_URL=https://gateway/v1/`（网关 / vLLM / OpenRouter 后挂）是常见配置，结果是 404 且错误信息只有 `request failed: 404`。

**这一节的教训与 §21.5 同构**：R1f 的"链上不可观察 ⇒ 静默消失"在 URL 这条链上重演了一遍，只是这次不可观察的是 `stream()` 内联的 `format!`。

### 22.5 另有两项计划外的发现

- `branch_summary.rs`（585 行）的 **compaction 半边已接线**（G7/R3a），但 **`/fork` 的 branch 摘要半边未接**：`begin_branch_summary()` 无生产调用点。§5 记的"从未接线"已不准确。
- `operations.rs`（333 行）**确为真零调用点** —— §5 这条仍成立，且它是 `provider_wire` oracle 所需的 mock 基础设施。

## 23. 第二阶段执行计划（2026-10-12）

### 23.1 排序原则

§22 的三条推翻共同指向一条排序原则：**先让门禁可信，再扩大能力面。**
在 oracle 无法证伪的代码上做重构，等于用"测试全绿"验收 —— 那是 §12 记的、已经付过三次代价的错误。

  │                    │
  └─► M2 R3 接线        └──► M4 auth / 扩展运行时（依赖 M1，且需 owner 决策）
  
M3 发布收口（独立，随时可做）
```

### 23.2 里程碑与验收（全部可证伪）

| # | 范围 | 验收（可证伪） | 依赖 |

## 24. M0 实施记录 —— URL 构造收敛（2026-10-12）

### 24.1 为什么先做它

§22.4 的两类缺陷（测试不接触生产代码 / 零覆盖藏缺陷）都在这条链上，且 M0 是整个第二阶段的门禁基础：
**M1 要重构 `openai.rs`，如果 URL 拼接仍不可观察，重构就是盲改。**

### 24.2 对齐的基准（不发明）

查 Pi 源码确认基准，不是凭直觉设计：

| Pi 位置 | 行为 |
|---|---|
| `pi-ai/src/api/mistral-conversations.ts:291` | `new URL("v1/chat/completions", baseUrl)` —— 相对 URL 解析 |
| `anthropic-messages.ts:887/911/948` | `baseURL: model.baseUrl` 交 SDK，SDK 拼 `/v1/messages` |
| `openai-responses.ts:251` | 同上，交 SDK |
| `providers/*.models.ts` | `baseUrl` 一律以 `/v1` 结尾、无尾斜杠（`https://api.together.ai/v1`、`https://openrouter.ai/api/v1`） |

**因此 nini 的目标语义是**：base 归一（去尾斜杠）后做相对解析 —— 用最后一段替换为 `v1/...`。
这与 `new URL("v1/chat/completions", base)` 在所有 https base 上等价，且对尾斜杠健壮。

### 24.3 改动

1. 新增 `crates/nini-ai/src/api_url.rs`：三个 `pub` 纯函数
   （`chat_completions_url` / `anthropic_messages_url` / `responses_url`）+ 归一核心
2. 三个 dialect 的 `stream()` 改为调用它们，删掉内联的 `format!`
3. `openai.rs` 的三个 URL 测试改为**调用生产函数**，`handles_trailing_slash` 的期望值从
   `//v1` 改为正确的单 `/v1`

### 24.4 证伪（三个注入，各命中不同的测试）

| 注入 | 结果 |
|---|---|
| 去掉尾斜杠归一（还原原逻辑） | 🔴 3 条红：`a_trailing_slash…`、`a_slash_is_insignificant…`、`the_path_is_appended_exactly_once`；其余 7 条**仍绿** |
| `chat_completions_url` 退回无条件加 `/v1`（v0.7.3 之前的 bug） | 🔴 3 条红，含 `a_base_that_already_ends_in_v1…` |
| **把 `anthropic_messages_url`「顺手修好」成跳过 `/v1`** | 🔴 **仅 1 条**红：`anthropic_reproduces_the_sdk_unconditional_append` |

**注入 3 是这次最有价值的一条，它证明的不是修复，是护栏。**
「base 带 `/v1` 会拼出 `/v1/v1/messages」看起来像 bug，任何人（包括下一轮的我）都会想去修它。
`anthropic_reproduces_the_sdk_unconditional_append` 让这个修法**必然变红**，
并在测试名与 doc 里写明这是对齐 SDK 的刻意行为。
注入后其余 9 条全绿 —— 护栏精确，不会误伤。

若当初把这三处统一成同一个函数（看起来更整齐），注入 3 与注入 1 就会同时失效。

### 24.5 一个副作用：fmt 忽然有了 diff

删掉那段跨行 `format!` 之后，`cargo fmt --check` 报出 `openai.rs` 的 `try_stream!` 宏体缩进不一致。

原因不是新代码写坏了：**原来的跨行 `format!` 让 rustfmt 判定宏体不可安全重排，于是整块被跳过**
（所以改动前 fmt 是「干净」的）。换成单行调用后这个前提消失，rustfmt 重新接管，
把一直存在的缩进问题一并暴露出来。`cargo fmt --all` 后宏体整体重排，
1183 个测试全部通过 —— 印证纯格式化无语义变更。

**教训**：「fmt 干净」可能意味着「rustfmt 没看这里」，而不是「这里写得整齐」。
与 §21.5「检索式检测器必须先校准」同源：**检查器的沉默不是通过的证据。**

## 26. nini-ext 判定 —— 路线已被证伪，不是"没接线"（2026-10-12）

§5 与 §7 把它列为「已实现但**从未接线**，780 行，接上即可」。§12.5 的 R2j 与本次审查都要求先核实这句话。
核实结果：**接上也不会通**。

### 26.1 证据

| | Pi 的扩展 | `nini-ext` |
|---|---|---|
| 单元 | `.ts` / `.js` **文件** | 编译后的 Rust `cdylib` |
| 加载 | `jiti`（`core/extensions/loader.ts:17`） | `libloading::Library::new` + C ABI 符号 `nini_ext_activate`（`loader.rs:110-120`） |
| 接口面 | `ExtensionAPI` **28 个运行时事件** + 可 `import` Pi 自己的包（`loader.ts:27`） | Rust `trait ExtensionAPI`，**6 个方法** |

`dlopen` 加载不了 TypeScript 文件，而 `dlopen` 是这个 loader 唯一的动作。
两者**没有交集**——不是缺一个调用点、不是缺一个事件，是**执行模型不同**。

真要兼容，需要同时具备：内嵌 JS 引擎 ＋ `ExtensionAPI` 28 事件的兼容层 ＋
在 Rust 二进制里解析 `import ... from "@earendil-works/pi-coding-agent"`。
**那是一个项目，不是一次接线。**

### 26.2 实际状态（已核验）

```

### 27.2 Bug 2 的决策：删掉 vim 键，而不是换键

两个绑定争 `Ctrl+K`。可选：给 `ScrollUp` 换个键。**选的是删掉两个 vim 绑定**，依据是 Pi 本身没有：

```
pi-tui/src/keybindings.ts:160-174
  tui.altScreen.pageUp      → ["pageUp"]     "Scroll viewport up one page"
  tui.altScreen.pageDown    → ["pageDown"]   "Scroll viewport down one page"
  tui.altScreen.halfPageUp  → []            "Scroll viewport up half a page"
  tui.altScreen.halfPageDown→ []
```

**Pi 没有任何 vim 风格滚动键。** nini 的 Ctrl+K/J 是自己发明的，而它正是与 readline 冲突的根源。
且 `Ctrl+K` 本身是 readline/bash/Pi 的 kill-to-end-of-line，一个键绑两个动作**无论顺序都不可能都对**。

`Ctrl+J` 多一条理由：它是 LF。多数终端回车发 `\r`（crossterm 解析为 `KeyCode::Enter`），当前不冲突；
但发 `\n` 的终端配置下，**回车会被滚动动作吞掉**。按风险记录，未断言为必现。

### 27.3 Bug 3 的修法：让渲染侧发布"一页 = 几条 line"

`scroll_offset` 的单位是 `TranscriptLine`，而一行渲染成多少 item 取决于内容。
按键侧**既没有视口高度也没有行高**，只能猜——它猜的是 `1`。

正确的做法不是再猜一个数，而是**在唯一同时知道两者的作用域里算**：
`render_transcript` 已有 `items_per_line` 与 `visible_height`，于是新增

- `AppState::page_lines: Arc<AtomicUsize>`（与 `item_cache` 同款 interior mutability，因为 render 拿 `&AppState`）
- `lines_needed_for_items()`：从底部数，与渲染侧跳过方向一致

**注意与 Pi 的差距**：Pi 的 `ScrollView.scrollBy()` 操作的是 `currentScrollTop`（**绝对 cell 位置**），
上限为 `contentHeight - viewportHeight`。nini 仍是"从底部跳过 N 条 line"。
**所以本修复让 PageUp 名副其实，但滚动模型未与 Pi 同构** —— 见 §27.6。

### 27.4 一处我以为修了、其实没有的

滚动指示器（`render.rs:906/919`）原本用 `label.chars().count()`，标签里是 `↑`/`↓`
（East-Asian-Ambiguous）。我把它改成了 `display_width()`，并在注释里写了"在 CJK 终端会错位"。

**然后去测 unicode-width 的实际行为：**

```
"↑" chars=1 width=1 width_cjk=2
"✅" chars=1 width=2 width_cjk=2
```

`unicode_width::width()` 对 Ambiguous **返回 1**，与 `chars().count()` 完全相同。
**这个改动没有行为变化**，只是一致性清理。注释与测试都已改写成如实陈述，
并命名为 `scroll_indicator_labels_agree_with_a_char_count_today` ——

## 28. 滚动条（2026-10-12）

用户指出：**Pi 的 TUI 右侧有一条滚动栏，nini 没有**。

### 28.1 这是一条"记录了但没接线"

`crates/nini-tui/src/theme.rs` 里**早就有 `scrollbarThumb`**（暗色 `#3a3a4a` / 亮色 `#d0d0e0`，
`theme.rs:551` 与 `:626`），而 `grep -rn scrollbar crates/nini-tui/src` 除 theme 外**零命中**。

键名是 Pi 的：`interactive-mode.ts:885` 用 `theme.bg("scrollbarThumb", text)` 给 thumb 上色。
所以**主题 schema 是照 Pi 搬过来的，组件从未跟上** —— 与 `set_status_bar_usage`、
`default_thinking_level` 完全同族（§21.3 的"记录了但没接线"）。

### 28.2 Pi 的规格（源码级，不发明）

| 项 | 位置 | 值 |
|---|---|---|
| 设置 | `settings-manager.ts:139` | `fullscreenScrollbar?: ScrollViewScrollbar; // default: "auto"` |
| 取值 | `scroll-view.ts:4` | `"hidden" \| "auto" \| "always"` |
| 可见性 | `scroll-view.ts:71-77` | `always` → 有视口即显示；`auto` → **溢出且最近活动过** |
| 淡出延迟 | `scroll-view.ts:49` | 1000 ms（`scrollbarHideDelayMs`） |
| 几何 | `layout.ts:266-291` | 见下 |
| 位置 | `layout.ts:288` | `column = rect.x + rect.width - 1`（**最后一列**）|
| thumb 高度 | `layout.ts:271-274` | `max(min(2, track), min(track, round(track²/content)))` |
| thumb 偏移 | `layout.ts:279` | `round(scrollTop / maxScrollTop × maxThumbTop)` |

**所以你看到的是 Pi 的默认行为**（auto），不是配置出来的。

### 28.3 关键：方向要翻转

Pi 的 `scrollTop` 从**顶部**量起；nini 的 `scroll_offset` 是"从底部跳过的 **line** 数"，
渲染也从底部往上跳。故：

```
scroll_top = (content_height - viewport_height) - items_skipped_from_bottom
```

**方向弄反是最显眼的错误** —— 模型正在流式输出时（`items_skipped = 0`）thumb 会停在顶部，
而读者期望它在底部。注入 H 专门钉住这一条。

数据侧**无需新增状态**：`items_per_line`（渲染时已算）、`total_items`（`contentHeight`）、
`visible_height`（`viewportHeight`）全部现成。唯一新增的是 `items_skipped_from_bottom`
的捕获——它在第二个循环里被消耗掉了。

### 28.4 transient 用时间戳而非定时器

Pi 用 `setTimeout` 在 1000 ms 后隐藏。nini 在 `AppState` 上存 `scroll_activity: AtomicU64`，
滚动动作写入，渲染时比较 `now - last < 1000`。**同样的结果，没有后台任务**，
且与 `page_lines` 共用同一套 interior-mutability 模式（render 拿 `&AppState`）。

### 28.5 与 Pi 的一处有意分歧

Pi 在 `always` 模式下把内容宽度减 1（`getContentWidth`）给滚动条让位。**nini 不让位**：
thumb 覆盖最后一列，而非重排转录区。理由：重排会让文字在滚动条出现/消失时**在读者眼前移动**。
auto 模式下 Pi 本来就不让位，所以这是把 `always` 的行为向 `auto` 靠拢。

### 28.6 未做：拖动

Pi 支持拖动（`tui-alt-screen.ts:114` `ScrollbarDrag`，带 `grabOffset` 使 thumb 保持抓取点）。
**nini 完全没有鼠标管线**——无 `EnableMouseCapture`、无 `MouseEvent` 分支。
这不是加一个控件，而是"nini 要不要接管鼠标"的决定。留待决策，不擅自引入。

### 28.7 e2e 抓到的两个真问题

**① thumb 只有一行。** 首版渲染 `"█".repeat(height)` 到一个 **1 列宽**的区域：
那是 2-cell 的 token，ratatui 裁剪成 1 个字符，**第二行往下全空**。
由"thumb 连续"的断言抓住。改为每行一个 `RLine`。

**② 我的测试辅助函数有 UTF-8 陷阱。** `last_column` 返回 `String`，
而 `String::rfind` 返回**字节偏移**。该列含 3 字节的框线字符，第二个 `█` 的**字节**偏移是 21，
测试因此报"thumb 在 18..21"，而 buffer 里 `█` 在 18 和 19。
**一个指向完全正确代码的失败**——已改用 `Vec<char>` 并在注释里写明原因。

（本轮至此已有 **6 次**"测试错、实现对"。第 2 次与第 6 次都发生在新写的测试辅助函数上。）

Pi 的 `scrollTo(scrollTop)` 一步到位，因为它的滚动量本来就是 cell。

故新增：`AppState::line_heights: Arc<Mutex<Vec<usize>>>`，由 render 每帧写入。
（没有复用 `item_cache`：它按 width 索引，miss 时取不到值。）

"抓在 thumb 顶部"，**拖动一开始 thumb 就会跳 3 行**。

发现路径值得记录：先是一个**假阳性的测试**（它用一次根本没发生的拖动来"证明" grab_offset 生效——
按压点 `thumb_top + 2` 落在轨道外），修好那个测试后才暴露出真实的类型缺陷。
**假阳性测试掩盖真 bug，是本项目第 N 次同型事故。**

用户问："我现在终端输入 nini 是否已经能启动最新的二进制，而不像上次那样
代码更新了而二进制落后。"

**先答事实，再答机制。**

```
~/.local/bin/nini -> /home/jin/nini/target/release/nini
```

软链本身没问题。真正的原因是三条事实叠加：

1. `install.sh:71` 下载**预构建压缩包**，`install.sh:94` 直接 `install`，
   **从不调用 cargo** ⇒ "已安装" 与 "是当前代码" 是**两件无关的事**
2. 软链指向 `target/`，而 `target/` 只在有人跑 `cargo build` 时前进
3. `nini --version` 两种情况都打印 `nini 0.9.1` ⇒ **没有任何可比较的东西**

第 3 条才是关键。前两条是所有 Rust 项目的常态；**只有第三条是本项目特有的失职**。

### 31.2 改动

`crates/nini-cli/build.rs`（新增）嵌入 commit / 构建时间 / dirty，
`--version` 打印：

```
nini 0.9.1 - 3caa078 +dirty (2026-10-14 17:20:27 +0800)
nini 0.9.1 - dc2bb16 (2026-10-14 17:23:39 +0800)
```

- `+dirty`：构建时工作区有未提交改动。**否则 commit id 会被读成"精确等于这个"**
- 构建时间用 `date` 而非新增依赖
- 无 `.git` 的环境（tarball / CI）可用 `NINI_BUILD_COMMIT` 覆盖

Pi 的 `--version` 是 `pi-coding-agent 0.84.2` —— 只有包名和版本，因为它从 npm
分发，**不存在"构建"这回事**。nini 从 checkout 构建且会过期，所以必须多说。

### 31.3 一个明确接受的代价

`rerun-if-changed=.git/HEAD`：提交会改变嵌入的 commit 并触发重新链接。

**即：提交不再是免费的，下一次 build 会重编二进制 crate（约 30–36 秒）。**

这是刻意的。它换来了"二进制能说出自己是谁"。若不接受这个代价，替代方案是
**只嵌入构建时间**（无需 rerun-on-commit），但那样就认不出"代码更新了"——
正是要解决的问题。

### 31.4 验证

`cli_e2e.rs` 两条：版本行含 commit 与时间戳、且不重复打印程序名
（首版写成 `nini nini 0.9.1`，clap 自己会加名字）。

实测：提交 → 重建 → `+dirty` 消失、commit 更新，**期间没有做任何手工同步**。

### 31.5 仍未收口

`CARGO_PKG_VERSION` 仍是 `0.9.1`，而 `dc2bb16` 已是 v0.10 的量。
版本号提升属于 P4（发布收口），需要一起处理 CHANGELOG 与远端推送。

## 32. session 锁 —— 十一处把竞争写成数据丢失（2026-10-16）

### 32.1 触发不是一条 CI 红灯

`7009e55` 的 run：`ubuntu` 红（`a3_seed::the_seed_carries_tool_calls_and_results`，
seed = `[]`），`macos` 绿 —— 而前一次 run 是 `macos` 红、`ubuntu` 绿。
两个"间歇"看起来无关。**它们是同一个缺陷的两端。**

v0.10 段里"macOS 不绿、ubuntu 通过"的结论已经被事实推翻，而 CHANGELOG
当时写下的正是这个结论。所以这一节先修的是**陈述**：结论过期而没人发现，
与代码缺陷是同一类病（记录了，但不再为真）。

### 32.2 先分类，再修（§31.8 的纪律）

`grep -rn 'try_lock()' crates/ --include=*.rs` 给出 11 处。逐一定性后，它们
不是 11 个 bug，是**一个类别在 11 个形态上**：

| # | 访问点 | 锁忙时的含义 | 定级 |
|---|---|---|---|
| 1 | `session_context_messages` | seed 为空 —— 模型带着零历史被提问 | P0 |
| 2 | `session_append_message` | 整个 agent turn 不落盘 | P0 |
| 3 | `session_push_message` | 用户/助手消息不落盘 | P0 |
| 4 | `session_compact` | 压缩静默不发生 | P1 |
| 5 | `transcript_from_context` | transcript 与 session 脱钩 | P1 |
| 6 | `session_flush` | 这次写盘被跳过，无任何日志 | P1 |
| 7-8 | `/tree`、分支摘要 | 空树；状态行卡在 "computing…" | P1 |
| 9-10 | `/fork` ×2 | "(fork: the session is busy)" | P2（已给用户提示）|

只修 1-3（我最初的建议）会把 4-10 留到下一次以别的症状回来 —— 这正是 v0.10
自己的主题。

### 32.3 根因是原语选错，触发它的竞争是自己造的

`state.rs:13-16` 的注释原文：

> `session` is held across `.await` points in the agent task, so it needs the async mutex.

**这句话是假的**，而且它是一条"看起来有依据"的注释 —— 这比没有注释更危险。
逐点核实：11 处访问点全是普通 `fn` 里的同步临界区；全仓只有一处
`.lock().await`，在 `nini-tools/mutation_queue`，另一个 crate、另一把锁。

`tokio::sync::Mutex` 的存在前提是 guard 跨 `.await`。给一把永不跨 `.await`
的锁，它就邀请 `try_lock`；`try_lock` 又把**正常竞争**变成"失败"，于是每一处
都要自己编一个失败答案，11 处编出 4 种语义（静默空 / `ok()?` / `if let` /
用户提示）。

竞争强度也是自己造的：`session_flush` 在 `std::thread::spawn` 的线程里
**持锁做 `write_to_file`**（整份 JSONL 序列化 + 临时文件 + rename），而每个
TurnEnd 都 flush。实测修复前 200 轮里有 **198 次读到空 seed**。

### 32.4 方案：换原语 + 把 IO 移出临界区 + 删掉谎话

| 改动 | 理由 |
|---|---|
| `tokio::sync::Mutex` → `std::sync::Mutex` | guard 不跨 await；poison 按 `lock_state` 既有范式 `unwrap_or_else(\|e\| e.into_inner())` 恢复 —— 一把锁里 panic 不会毁掉 session，为此永远拒绝读取才是把可恢复 panic 变成数据全失 |
| 11 处 `try_lock()` → `state::lock_session(&arc)` | 竞争不再是错误语义，只剩等待 |
| `session_flush` 锁内 `clone`、锁外 `write_to_file` | `Session` 已 `derive(Clone)`；不缩短临界区的话，"让读者等待"只是把静默丢失换成界面卡顿 |
| 写盘错误 `eprintln!` → `tracing::error!` | 丢一次写盘是用户看不见的损失（transcript 有、文件没有），而 v0.10 刚把 `tracing` 接上 |
| `/fork` 两处 "the session is busy" 删除 | 锁不会再"忙"，只会等 —— 那条提示只能是**对用户说的谎** |

**被否决的备选**（记下来，避免下次重想）：

- **只改 flush（clone 出锁）**：治标。竞争窗口从 ms 降到 µs，但 11 处静默降级
  原样保留，数据路径仍是概率性正确。
- **有界重试 + try_lock**：仍是概率性正确。数据路径不该概率性正确。
- **RwLock**：session 是低频访问，并发读收益不抵复杂度；tokio RwLock 同样不
  能跨 await 阻塞。
- **`blocking_lock()`**：`#[tokio::main]`（multi_thread）上下文里对
  `tokio::sync::Mutex` 调用会 panic —— 直接排除。
- **把 flush 改成单 worker 队列**：能顺带解决线程堆积，但那是**另一个**缺陷
  （见 32.6），不该混进这次。

### 32.5 证伪：3/3 红，而且我先写错了两遍

`git stash push -- crates/nini-tui/src/`（测试文件 untracked，保留）后：

```
test flushing_does_not_make_the_seed_disappear ... FAILED
test a_contended_read_yields_the_context_not_an_empty_seed ... FAILED
test a_contended_append_is_still_recorded ... FAILED
test result: FAILED. 0 passed; 3 failed
```

两次自身错误（都写进了测试文件注释）：

1. **第一版用 `session.lock()`** —— 对 `tokio::sync::Mutex` 不编译，于是旧代码上
   测试**编译失败而不是变红**。跑不了的测试不是 oracle。改用两种原语都有的
   `try_lock`，测试才在旧实现上真正跑到断言。
2. **第二版把锁交给 spawn 线程后立刻读** —— 持锁线程往往还没被调度，于是
   "竞争的测试"没有发生竞争，**在它要抓的那份代码上通过了**。这是本次最危险
   的一个错误：它给出的是假绿。现在持锁线程拿到锁后先发信号再 sleep，主线程
   等信号到达才读。

### 32.6 未做（边界写清楚，避免含糊）

- **macOS `agent_wire_e2e` SIGSEGV**：仍在，Linux 无法复现（含 2 核 pin）。
  `7009e55` 加的 `RUST_BACKTRACE=1` 已就位，等一次可复现。**本次没有它就不会好**，
  也不假装会好。
- **flush 线程堆积**：每个 TurnEnd `thread::spawn` 一个线程，长会话会累积线程。
  既有行为，与本次锁修复正交；单 worker 化留待单独一轮。
- **`cargo test --workspace --all-targets` 本地 1360 全绿不构成 CI 证据**：原缺陷
  在本机 12 次连跑都不复现，唯一的判据是下一次 CI run。

v0.10 的 12 类修复**从未写入本计划**（本计划停在 §31 `--version`，10-14）。

## 33. turn divider —— Pi 从不画的那条线（2026-10-16）

### 33.1 报告与复现

用户报告"渲染还有长横线"。按 §31 的纪律，先复现再解释，不猜：

```
tmux new-session -d -s s -x 100 -y 40 './target/release/nini --provider fixture'
→ /help → 提问 → capture-pane
```

在 100/60/50/40 四种宽度下量到的东西：

| 终端宽度 | 屏幕上的长度 |
|---|---|
| 100 | 60（悬在屏幕中间）|
| 60 | 60 |
| 50 | 50（被裁）|
| 40 | **40 —— 满宽** |

满宽那一行就是用户看到的东西。而"40 时满宽"这件事本身说明：**divider
根本不知道宽度有多���**，终端只是替它裁了一下。

### 33.2 全仓扫描：产生 `─` 的产品代码只有一处

```
$ grep -rn '─' --include=*.rs crates/nini-tui/src crates/nini-cli/src
rich.rs:443:    let div: String = "─".repeat(60);
```

其余命中是 `push_user("└─ …")`（`/tree` 的树形连接符，Pi 同样有）和
测试里的断言。所以问题只有一根，不需要再找第二根。

### 33.3 Pi 的基准：没有这条线，而且 Pi 的线是按宽度算的

- **分隔用空行**：Pi 每一个消息边界都是 `Spacer(1)` ——
  `assistant-message.js:74/121/131/139/144`、`bash-execution.js:30`、
  `branch-summary-message.js:30`、`compaction-summary-message.js:31`。
  **没有一处画线。**
- **唯一的线按宽度算**：`dynamic-border.js:18`
  `"─".repeat(Math.max(1, width))` —— 输入框边框。nini 抄了它的样式，
  没抄它的宽度概念，于是那条线只存在于"输入框"这一处。

结论不是"渲染算错了"，而是**这是一个 nini 自己发明的元素**，长度是当年
随手写的，且被测试 `render_divider_is_sixty_dashes`（`assert_eq!(count, 60)`）
固化成了规格。`git log -S push_divider` 指向 `7eb7d91`（v0.4.0 首次发布）——
它从第一天就在，从没被审过。

### 33.4 为什么不选"改成宽度自适应"

方案 B（宽度取实际可用宽度）只改 3 行，但它保留了一个 Pi 不存在的元素。
项目的目标是 Pi 兼容（README 第一句），一条 Pi 不画的线是对标缺口而不是
nini 的特色。**宽度自适应会让缺陷变得不难看，而不是让它消失。** 选了 A。

### 33.5 改动面：远小于预期，因为没动调用点

`push_divider` 有 20+ 调用点，若逐个删除，会牵动 6+ 处测试的行数断言
（`agent_wire_e2e.rs:477/493/536` 的 `lines.len() == 2 // user + divider`）。
**改渲染而不是改结构**：

- `rich::render_divider(&Theme)` → `rich::turn_separator()`，返回**一行空格**
- `render.rs` 的 `TranscriptLine::Divider` 分支改调它（1 行）
- `TranscriptLine::Divider` 枚举与 `push_divider` **原样保留**

理由：turn boundary 的**语义**没变，变的是画法。改结构会去动 20+ 处与
视觉无关的代码，而改动语义本身不成立。

用**一个空格**而不是空字符串：ratatui 把空 `RLine` 量成 0 行高，空行会
消失 —— 那就把分隔也一起删掉了，而这正是那条线当初要干的事。

### 33.6 证伪

`git stash push -- crates/nini-tui/src/`（测试保留）：**0 passed, 2 failed**

```

```

40 列 × 2 条边界 = 80，缺陷被精确计数。

两条 oracle 用**基线对比**（有边界的帧 vs 空 transcript 的帧，横线数必须
相等）而不是数固定行号：prompt 自己的边框是合法的 `─`，数坐标等于把布局
写死进测试，footer 一改就假红。

### 33.7 一条被牵连的既有测试

`transcript_width_e2e::clear_while_scrolled_up_resets_the_viewport` 红了：
它用"divider 仍然可见"作为**渲染管线还活着**的证据。证据随规则一起没了。

**处理方式是把探针换成有内容的行，不是把规则画回来。** 测试的目的
（clear 后视图被重置、渲染没坏）没有变，变的只是它当初选错了证人 ——
这也是 §24.6「一次副作用」的同类：改一个断言会撞到另一个断言。

### 33.8 保留的

那是同一段间距在 HTML 里的写法；而打印/长文阅读里可见分隔仍然有用。

## 34. 第二个横线来源 —— markdown `---`（2026-10-16）

### 34.1 用户报告否定了 §33 的结论

§33 交付后，用户报告："**长任务到后期还是出现横线**"，且侧边栏有问题。

按 §33 的纪律重做 tmux 端到端，但这次**换场景**：起一个本地
openai-compat 假 LLM（`fake_llm2.py`，SSE），让 nini 跑多轮真实对话。

§33 的 fixture 场景（turn divider）已经干净，但 §33 的**扫描方法**有缺陷：

```bash
grep -rn '─' --include=*.rs crates/nini-tui/src/ | grep -v '///' | head
```

这条命令有两个盲点：

1. **字面量 vs 转义**：`markdown.rs` 写的是 `"\u{2500}".repeat(60)`，
   不是 `"─"`。grep 字面量 `─` 匹配不到它。
2. **`head` 截断**：输出被截断，看起来"只有一处"。

§33.2 那句"全仓扫描：产生 `─` 的产品代码只有一处"**是错的**。
教训：**扫描的完备性要用反例验证**，不能靠"grep 没输出"下结论 ——
尤其当代码库存在两种等价写法时。

### 34.2 找到的第二根线

在假 LLM 的返回里放 markdown `---`（真实模型在长回答里极常用）：

```
line 4: ─= 60      ← markdown thematic break
line 37: ─= 89     ← 输入框
```

`markdown.rs:466`，连注释都承认了问题的形状：

```rust
// Use the full terminal width — but we don't know it here, so use a
// generous default. ratatui's wrap will clip anyway.
let rule = "\u{2500}".repeat(60);
```

**注释的前提是假的**：`rich.rs` 的 `render_assistant_message(text, theme,
max_width)` 手里就有 `max_width`，同一行还给其它构造器传了宽度，只有
`render_markdown(s, theme)` 没拿到。

### 34.3 Pi 的规格

`@mariozechner/pi-tui` `dist/components/markdown.js:308-312`：

```js
case "hr":
    lines.push(this.theme.hr("─".repeat(Math.min(width, 80))));
```

两半都要：`width`（线必须有宽度概念）+ **80 上限**（否则宽屏上就成通栏带）。

### 34.4 为什么它在 60 列以下是"正确"的 —— 这就是它藏住的原因

`rich.rs` 渲染完统一 `truncate_line_cells(max_width)`：

| 终端宽度 | 旧实现实际 | Pi |
|---|---|---|
| 40 | 40 ✓ | 40 |
| 60 | 60 ✓ | 60 |
| 100 | **60 ✗** | 80 |
| 200 | **60 ✗** | 80 |

**缺陷只在 60 列以上可见**，而 60 列以上正是绝大多数人的终端。所以：
盯着窄终端测，永远测不出来。

### 34.5 改动

- `render_markdown(s, theme)` → `render_markdown(s, theme, width: Option<usize>)`
- `MdState` 持 `width`；`on_rule` 用 `rule_width() = width.map_or(1, |w| w.min(80).max(1))`
- `rich.rs` 传 `max_width`
- 无宽度时画 1 个字符：不知道宽度时，**诚实是最短的一条线**，不是 60 的猜测

### 34.6 我在到达可证伪的 oracle 上又犯了同一个错（第二次）

第一次把 oracle 写进 `markdown.rs` 的 `#[cfg(test)]` → stash 源码时被一起回退
→ 证伪失败。

第二次写进集成测试文件，但直接调 `render_markdown` → **编译失败**
（`render_markdown` 正是加参数的那个函数）。**编译失败不是证伪。**

第三次：改调 `render_assistant_message(text, theme, max_width)` ——
这个签名在修复前后都存在 → 旧代码上真跑、真红：

```
1 passed; 3 failed
  expected the minimal rule when no width is known, got 60
  each rule must follow min(width, 80), not a constant: [60, 60]
```

**规律**：修复若改变签名，oracle 必须走**签名未变的更高层 API**。
（同 §33 的教训：证据必须能在缺陷代码上运行。）

## 35. ESC 中止后的输入死区（2026-10-16）

### 35.1 报告与实测时间线

用户报告："nini 运行时按 esc 键不能插入对话"。

用慢 provider（DELAY=8）在 tmux 里测：

| 时刻 | 状态栏 | footer | 输入 |
|---|---|---|---|
| 发消息后 2s | `⠦ working…` | `Esc abort` | 被忽略 |
| ESC 后 2s | `idle • aborted` | `Enter retry  Esc clear` | **被丢弃** |
| ESC 后 6s | `idle` | 正常 | 恢复 |
| ESC 后 16s | `idle` | 正常 | ✓ |

**不是永久卡死**，是**约 4 秒的输入死区**。

### 35.2 根因：一个没人走出来的状态

`KeyAction::Abort`（`runtime.rs:1636`）设 `RunMode::Aborted`。

而**所有输入路径的门禁都是 `mode == Editing`**：

- `handle_key` 的 Insert 分支（`runtime.rs:1423` 等 11 处）
- `submit_user_input`（`runtime.rs:1942`，`!= Editing` 直接 return）
- 编辑器自身的处理器

全仓 `RunMode::Aborted` 只出现在 6 处：2 处**设置**、1 处 footer、1 处测试、
2 处测试 helper。**没有任何一处把它改回 Editing**。唯一的出口是 agent 流结束时
推送的 `Done`（`runtime.rs:363`）——而那要等被中止的 run 自己收尾。

所以 ESC 之后到 Done 之前，敲的每一个键都被静默丢弃：无回显、无提示、状态不变。

### 35.3 Pi 的基准：中止是同步的

```js
// interactive-mode.js:2219
this.defaultEditor.onEscape = () => {
    if (this.session.isStreaming) {
        this.restoreQueuedMessagesToEditor({ abort: true });
    }
    else if (this.session.isBashRunning) { this.session.abortBash(); }
    else if (this.isBashMode) { this.editor.setText(""); this.isBashMode = false; }
    else if (!this.editor.getText().trim()) { /* 双击 ESC → /tree, /fork */ }
};
```

两个关键点：

1. **Pi 根本没有 "aborted 模式"**。编辑器是一个独立组件，
   `isStreaming` 不影响它能否打字 —— 这不是门禁问题。
2. **`restoreQueuedMessagesToEditor`** 说明 Pi 还支持**运行中输入并排队**，
   ESC 中止时把排队的消息取回编辑器。

nini 的 `RunMode` 门禁 = 把"能否输入"绑到"当前状态"，Pi 则不这么做。

### 35.4 第二条：footer 承诺了一个不存在的功能

`RunMode::Aborted => vec![(" Enter ", "retry"), (" Esc ", "clear")]`

而 `submit_user_input` 里**没有 Aborted 分支**（`!= Editing` 直接 return）。
`Enter retry` 提示了一个按下去什么都不会发生的按键。

这与 v0.9.2「Things that told you they worked when they didn't」同一族：
提示与实现分离，且**测试还把它固化了**（`footer_aborted_mode_shows_retry`
断言 `text.contains("retry")`）。

### 35.5 改动

1. 删除 `RunMode::Aborted`（枚举 + footer 分支 + 2 处测试）
2. `handle_key` / `apply_action` 的 abort 分支：回到 `Editing`，
   保留 `status = "aborted"` 让用户看到"这一轮被中断了"
3. `no_mode_advertises_a_key_that_does_nothing` 守住"不承诺不存在的按键"

### 35.8 仍未对齐（明确记下）

**运行中不能输入。** Pi 接受并排队（`_pendingNextTurnMessages` /
`restoreQueuedMessagesToEditor`），nini 在 `mode == Running` 时拒绝一切输入。

nini 已有 `pending_next_turn_messages`，但它只在**压缩期间**使用，不是给
"运行中用户输入"用的。完整对齐 Pi 需要：运行中输入进入队列 → 下一轮与新消息
一起发送 → ESC 中止时把队列恢复到编辑器。工作量不小，且会改动提交路径的
语义，**单独立轮**。
