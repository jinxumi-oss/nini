### P0-3 补记（实施 P0-2 时挖出，比 P0-2 更严重）

`truncate()` 切字节预算用的是裸 `&kept[..half]`，`half` 是任意字节下标：

```
panicked at src/bash.rs: end byte index 524288 is not a char boundary;
it is inside '文' (bytes 524286..524289 of string)
```

**项目在 v0.8.4 修过两次同一类 bug**（`render_tool_call`、`render_bash_execution`），`truncate` 两次都漏了。区别在于它在**工具执行路径**上：一条超过 1 MiB 的中文 bash 输出，会 unwind 掉整个 agent 任务，不是只坏一个面板。812 个测试全绿，因为所有 fixture 都是 ASCII。

## 2. 逐条：现象 · 证据 · 根因 · 修法

### P0-1 — bash 超时杀不掉自己的进程组，且恒定多等 5 秒

**现象**：`bash` 工具的 `timeout` 到点后，**`killpg` 完全没有生效**。子 shell 一直活到 grace 超时后被 `kill_on_drop` 收尸。工具描述里承诺的 "on timeout the process tree is killed"（`bash.rs:74`）和文件头注释（`bash.rs:5` "on timeout (`setsid(2)` on Unix") 对 `BashTool` 这条路径**是假的**。

**证据 1 —— 进程组根本不存在**

按 `bash.rs:115-125` 的方式（`Command::new($SHELL).arg("-c")`，无 setsid）spawn 一个子进程后实测：

```
self pid=550786 pgid=550786
child pid=550789
child's real pgid (read /proc/550789/stat field 5) = 550786
killpg(child_pid=550789) target group exists? false
```

子进程没有 setsid，所以它的 PGID = 父进程的组（550786），而它自己**不是组长**。`kill_process_tree` 却拿 `child.id()` 当 PGID 去 `killpg(550789)` —— **这个进程组不存在**，内核返回 ESRCH，代码里 `let _ = killpg(...)` 把错误吞了（`bash.rs:253`、`bash.rs:285`）。

**证据 2 —— 每次超时多花 5.1 秒**

请求 `timeout: 1`，实测 `elapsed = 6.17s`（PROBE-C / PROBE-A 两次一致）。
= 1s（超时）+ 5000ms（`KILL_GRACE_MS`）+ ~170ms。shell 在整个 grace 期间没死，最后是 `timeout(...)` future 过期 → `child` 被 drop → `kill_on_drop(true)` 生效才收掉。

**根因**：`bash.rs:124-125` 的注释写着 "Implemented inline in execute via pre_exec; nothing to do here" —— **但 `bash.rs` 里根本没有 `pre_exec`**。全仓 `pre_exec` 只出现在 `bash_runner.rs:118`。两条 bash 实现分叉了：

| 路径 | setsid | 谁在用 |
|---|---|---|
| `BashTool::execute`（`bash.rs`） | ❌ 无 | **LLM 的 bash 工具调用走这里** |
| `BashRunner::run_blocking_with_timeout`（`bash_runner.rs:110-125`） | ✅ 有 | hook 的 `BashOperations` |

**修法**：把 `bash_runner.rs:110-125` 的 `pre_exec(libc_setsid)` 整块搬进 `bash.rs:115-125`，让子 shell 成为组长，`killpg(child_pid)` 才有意义。同时把 `KILL_GRACE_MS` 降到 500ms —— setsid 到位后 SIGTERM 就能打中整组，5 秒是给失效路径兜底的。

**验收**：
- `child_pgid_equals_child_pid`：spawn 后读 `/proc/<pid>/stat` 第 5 字段，断言 `pgid == pid`（容器内也成立）
- `timeout_does_not_wait_full_grace`：`timeout: 1` 的调用总耗时 `< 2.5s`
- `timeout_kills_grandchildren`：`sh -c 'sh -c "sleep 999"' & wait`，超时后 `pgrep -f "sleep 999"` 为空

### P0-2 — bash 输出先全量进内存再截断，海量行 OOM

**现象**：`truncate()` 在**读完整个输出之后**才跑。中间的 `read_to_end` 没有任何上限。`max_output_bytes`（默认 1 MiB）只是个事后 cosmetic 指标。

**证据**：`yes ABCDEFGHIJ | head -c 67108864`（64 MB）执行成功，回报

```
PROBE-B ok in 2.31s; content len=22063
details: {"original_bytes": 67108864, "original_lines": 6100806, "truncated": true}
```

返回给模型的只有 22 KB，但**峰值内存里躺着 64 MB 原始字节 + 64 MB `from_utf8_lossy` 拷贝 + `lines().collect()` 对 610 万行分配的 610 万个 fat pointer（≈ 50 MB）**。

**放大路径**：`agent.rs:1154` 的 `FuturesUnordered` 无并发上限，模型一次发 20 个 bash 工具调用就是 20 份同时驻留。一次 `yes`、`find / -name '*.rs'`、或高噪声 `cargo build` 就够把 agent 打死。

**根因**：
- `bash.rs:138-141`：`stdout.read_to_end(&mut buf).await` —— 无上限
- `bash.rs:193-195`：`truncate(&raw, ctx.max_output_bytes, ...)` —— 读完之后才调
- `bash.rs:299-329`（`truncate`）：先 `initial.lines().count()`，再 `initial.lines().collect::<Vec<&str>>()`，两次全量遍历 + 全量分配

**修法**：
1. 读的时候边读边计数：累计字节 > `max_output_bytes` **或** 行数 > `max_output_lines * 2` 即停止累积，剩余部分 continue drain 到 null（避免 pipe 写端阻塞子进程），并在结果里标注 `truncated_by: "stream_cap"`
2. `truncate` 改成单趟扫描：先按字节预算切，再在切出的片段上按行数预算切，不再 `collect()` 全部行

**验收**：
- `huge_output_is_capped_in_memory`：跑 `yes | head -c 20MB`，用 `getrusage`/读 `/proc/self/status` 的 `VmHWM` 断言峰值增量 < 4 MB
- `truncate_handles_millions_of_lines_in_one_pass`：直接调 `truncate()` 传 100 万行输入，断言耗时 < 200ms 且输出正确

### P1-3 — transcript 宽度处理只覆盖 tool_result，其余行被静默裁掉

**现象**：只有 `tool_result` 一种行类型接了终端宽度。用户消息、assistant 正文、tool_call 头、bash 输出**全部**被 ratatui 在屏幕边缘直接切掉，**没有任何省略号**。

**证据**（40 列终端实拍）：

```
PROBE 1  user msg 210-char 单行
 2|> STARTAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA|      ← 输入是 START + 200×A + END，"END" 消失，无 …

PROBE 7  assistant 长段落
 2|START cccccccccccccccccccccccccccccccccc|      ← 同样静默裁掉

PROBE 5  bash 单行 1500 字节输出
 3|  qqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqqq|      ← 1500 字节只剩 37 字符，且 1500 < 2000 连字节提示都没有

PROBE 2  tool_call 头 200 字符 args
 2|▸ bash "command":"xxxxxxxxxxxxxxxxxxxxxx|      ← 见下

PROBE 8  CJK tool_call args（60 个「文」= 180 字节 / 120 单元）
 2|▸ grep 文 文 文 文 文 文 文 文 文 文 文 文 文 文 文 文 |   ← 屏幕 40 列只放得下 20 个字
```

**根因**：`render.rs:619` 用 `List` 渲染 transcript。**ratatui 的 `List` 不做 wrap** —— 它逐行写进 buffer，超宽直接截断。只有 `items_for_line` 的 `ToolResult` 分支（`render.rs:696-702`）计算了 `max_w` 并往下传，其余分支一律不传。

`rich.rs` 里的截断逻辑本身也有两个错误：

1. **`render_tool_call`（`rich.rs:87`）用 120 字节当预算**。ASCII 120 字节 = 120 单元，在 80 列终端上 `…` 落在**第 120 列、屏幕外** —— **截断标记自己被截掉了**。现有测试 `render_tool_call_truncates_long_args`（`rich.rs:490`）断言的是字符串层 `joined.contains('…')`，所以**测试假绿**，实拍里一个 `…` 都看不到。
2. **`markdown.rs:469-470` 的注释假设错误**：*"Use the full terminal width — but we don't know it here, so use a generous default. ratatui's wrap will clip anyway."* —— `List` 不 wrap，clip 是无提示的硬裁，不是"兜底"。

**修法**：
1. `width.rs` 新增 `pub fn truncate_cells(s: &str, max: usize) -> String`：按 unicode-width 累加到 `max - 1` 单元后接 `…`；`max == 0` 返回空串。已有的 `rich.rs:239-253` 那段逐字累加逻辑搬进去复用
2. `render_user_message` / `render_assistant_message` / `render_tool_call` / `render_bash_execution` 全部加 `max_width: Option<usize>` 参数
3. `items_for_line`（`render.rs:658-680`）在**所有**分支统一计算 `max_w` 并下传
4. `render_tool_call` 的 120 字节预算换成 cell 预算，缩进/前缀宽度一起算进去

**验收**（全部是 TestBackend 实拍断言，禁止只断言字符串层）：
- `long_user_message_shows_ellipsis`：40 列 + 210 字符 → 末字符是 `…`
- `long_assistant_paragraph_shows_ellipsis`
- `tool_call_ellipsis_is_on_screen`：80 列 + 200 字节 ASCII args → 帧里能 grep 到 `…`
- `cjk_tool_call_args_respect_width`：60 个「文」→ 渲染行 display_width ≤ 40 且含 `…`
- `bash_output_long_line_shows_ellipsis`

### P1-4 — tool_result 的「N more bytes」是死指标

**现象**：v0.8.7 把 2 KB 字节预算换成了 cell 预算，但**没删掉基于 2 KB 的 `hidden_bytes` 计算**。于是这个数字既可能凭空出现，也可能凭空消失，还可能严重偏小。

**证据**：

```
PROBE 3  单行 1500 字节（< 2000）
 3|  yyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyyy…|      ← 丢了 ~1460 字节
                                                            ← 但没有任何 "more bytes" 提示（hidden_bytes = 0）

PROBE 4  5 行 × 1000 字节（合计 5000，行数 5 < max_lines 8）
 8|  …(2 KB hidden)                       |      ← 实际丢了 ~4815 字节 ≈ 4.7 KB
```

**根因**：`rich.rs:266`

```rust
let hidden_bytes = linked.len().saturating_sub(TOOL_RESULT_PREVIEW_MAX_BYTES);
```

`TOOL_RESULT_PREVIEW_MAX_BYTES` 在 v0.8.7 之后**只剩这一个减法在用**（全仓 grep：另两处是文档注释），截断本身早就不按 2 KB 做了。这个数字现在纯属虚构。

**修法**：在 `rich.rs:239-253` 的逐行截断循环里累计**真正被丢弃的字符数**，用它算 hidden；同时统计被整行丢弃的行数。`TOOL_RESULT_PREVIEW_MAX_BYTES` 删除或重新定义为流式读取上限（与 P0-2 统一）。

**验收**：
- `hidden_bytes_matches_actual_loss`：1500 字节单行 → 提示里的数字 ≥ 1400
- `hidden_bytes_over_2kb_lines_is_exact`：5×1000 字节 → 提示 ≈ 4.7 KB 而不是 2 KB
- `no_truncation_no_indicator`：短内容 → 一行提示都不出现

### P1-5 — compaction / clear 不重置 `scroll_offset` → transcript 全空白

**现象**：用户向上滚动（PageUp）后触发 auto-compaction，transcript 变成**整片空白**，只剩角落一个虚高的 `↓ 59 more`，按任何键都恢复不了，只能一路滚到底。

**证据**（40×24，60 条每条展开 ~5 行的 tool_result）：

```
=== compaction 前 ===
 2|✓ read Took 1ms                         |
 3|  row0-0                                |
...
--- auto_compact_local folded 30; lines now 31 ; scroll_offset still 59 ; autoscroll false
=== compaction 后 ===
 0|[no session]                            |
 1| nini   idle                           m|
 2|                                        |
 3|                                        |
 4|                                        |      ← transcript 区 18 行全空
 ...
```

**根因**：
- `state.rs:1359` `auto_compact_local` 用 `drain(..cut_at)` 把行数砍半，**不动 `scroll_offset` / `autoscroll`**
- `runtime.rs:906` `action:clear` 直接 `lines.clear()`，同样不动
- `render.rs:576-618` 的 user-scroll 分支从底部累加 skip；skip 总量超过 `total_items` 时 `budget` 永远耗不完 → `visible_items` 为空 → 整片空白
- 顺带：`↓ N more` 直接用 `scroll_offset` 原值（`render.rs:634`），不 clamp，所以显示 59 这个不存在的行数

（`runtime.rs:1418-1422` 的 `max_offset = lines.len()-1` 只挡住了按键路径，挡不住"行数变少"这条路径。）

**修法**（双保险）：
1. `auto_compact_local` / `action:clear` 之后重置 `scroll_offset = 0; autoscroll = true`
2. `render_transcript` 入口加防御：`scroll_offset = scroll_offset.min(total_lines.saturating_sub(1))`；user-scroll 分支算完后若 `visible_items.is_empty()`，回退到 autoscroll 尾部视图；`↓ N more` 用 clamp 后的值

**验收**：
- `compaction_while_scrolled_keeps_content`：复刻 PROBE-I，断言 compaction 后 transcript 区非空且能看到 summary 行
- `clear_while_scrolled_resets_view`
- `scroll_beyond_end_falls_back_to_tail`：`scroll_offset` 设成 `usize::MAX`，断言非空

### P2-7 — `read` 无硬上限

`read.rs:87` `let limit = parsed.limit.map(...).unwrap_or(usize::MAX);` + `fs::read_to_string` 全量读 + `lines().collect()`。2 GB 的文件直接进内存，且 system prompt 里只有一句软提示（`read.rs:117` "For files >~1MB, use offset + limit"）—— 模型不听话就 OOM。

**修法**：`limit` 默认 2000 行；加 `max_read_bytes`（默认 4 MiB）硬上限，超出返回 `ToolError::InvalidArgs` 并在 message 里给出建议的 offset/offset+limit 组合。

### P2-8 — mutex poison 级联

`runtime.rs` 里有 38 处 `shared.lock().unwrap()`（还有若干 `completion.as_mut().unwrap()`）。只要有**任何**线程在持锁期间 panic，锁被毒化，之后每一次 `lock().unwrap()` 都 panic → TUI 永久死掉，且 `runtime.rs:317` 这种在事件循环最前面的 unwrap 会立刻把整个循环打死。

**修法**：`state.rs` 加 `pub fn lock_state(shared: &Mutex<AppState>) -> MutexGuard<AppState>`，内部 `unwrap_or_else(|e| e.into_inner())`，全量替换。`.as_mut().unwrap()` 改成 `if let Some(...)`。

### P2-9 — session JSONL 单行损坏 → 整个 session 不可读

`nini-session/src/lib.rs:308` 对每行 `serde_json::from_str(&line).map_err(...)?` —— 任何一行坏（手改、磁盘满、跨版本字段）整个 session 就打不开，**没有任何抢救**。写侧是 tmp+rename 原子写（`lib.rs:336-368`），所以自身崩溃不会写坏；但外部损坏没有兜底。

**修法**：坏行 `eprintln!` 一行警告后 `continue`，并在返回的 `Session` 上带 `skipped_lines: usize`，让 TUI 能提示"已跳过 N 行损坏记录"。

### P2-10 — 并行 tool call 无并发上限

`agent.rs:1154` `FuturesUnordered` 直接把 N 个 tool_call 全部塞进去。模型一轮发 30 个 bash 就是 30 个 shell 进程树同时 fork（每个还都会全量缓冲输出，见 P0-2）。`should_stop_after_turn` / hooks 也没有节流点。

**修法**：加 `RunConfig::max_parallel_tools`（默认 8），用 `for chunk in tool_calls.chunks(max)` 或手写 semaphore 限流。事件流与 `tool_results_slots` 的按 idx 回填逻辑（`agent.rs:1186-1194`）不变，所以**不影响 v0.8.8 的 id 匹配**。

### P2-11 — abort 时不发 ToolResult → TUI 永久 pending

`agent.rs:1204-1210`：abort 分支 `set_phase(Idle)` → yield `PhaseChanged` → yield `Aborted` → `return`，**不补发任何 ToolResult**。TUI 里那一轮已经画出来的 `▸ read` / `▸ bash` 永远停在 pending 状态，只能重启会话。Pi 在这里是发 canceled result 的。

**修法**：abort 分支 return 前，把 `tool_results_slots` 里所有仍是 `None` 的位置补一个 `ToolOutput::err("[aborted] …")`，走正常 `AgentEvent::ToolResult` 通道。顺带在 `Aborted` 之前 yield 一个 `PhaseChanged(Idle)` 已有，保持不变。

### P2-12 — 极小终端布局崩坏

实拍 5×3 / 10×4：footer 消失、输入框边框被压成 `┌ ─ input┐`、40×3 时 session 行整个不见。**不 panic**（ratatui 兜底），但用户会觉得界面崩了。

**修法**：`render.rs:95-102` 的 Layout 加 `Constraint::Min(1)` 下限；高度不足时按 `h < 6` / `h < 10` 分级砍 key hints / 输入框边框。

## 4. 测试纪律（本轮新增的硬规则）

P1-3 之所以能潜伏到现在，根因是**测试断言的是字符串层，不是渲染层**。`rich.rs:490` 的 `render_tool_call_truncates_long_args` 断言 `joined.contains('…')` —— 字符串里确实有 `…`，但屏幕上没有。测试全绿，用户看到的是另一个东西。

所以本轮所有渲染相关测试必须：

1. 走 `TestBackend` + `render_frame` 实拍，**断言单元格内容**
2. 宽度类断言用 `display_width()` 数**单元**，不用 `.len()` 数**字节**
3. 至少有一条 `40x24`（窄）和一条 `120x40`（宽）的对照，防止"只在一种宽度下对"
4. 单元测试里禁止出现"渲染函数返回的 Vec 里 contains(某字符)"这种**不经过 Frame** 的断言 —— 除非同时有一条等价的实拍断言

`crates/nini-tui/tests/` 现有的 4 个 e2e 文件（`tool_identity_e2e` / `transcript_overflow_e2e` / `tui_e2e` / `typography_snap`）已经有 `frame_dump()` helper，直接复用。

## 6. 明确不在范围

- **不做终端宽度变化的 wrap 重排**（Pi 的 `Paragraph::wrap` 行为）。本轮只保证「不静默丢内容 + 明确告知丢了多少」，不做软换行
- **不做 session 格式升级**。v0.8.8 加的 `id`/`name` 字段靠 v4 codec 的任意字段兼容就够
- **不做工具路径沙箱**。`read`/`write`/`edit` 不做目录越界检查是 Pi 的设计（agent 需要访问任意路径），不是本轮要修的漏洞
- **不修 ReDoS**。`grep`/`find` 用 Rust `regex` crate，本身是线性时间，已确认无灾难性回溯
- **不重写 `render_transcript` 的 item-space 数学**。v0.8.7 的实现经实拍验证正确（scroll_offset=1/3 都对），本轮只加 clamp 防御
