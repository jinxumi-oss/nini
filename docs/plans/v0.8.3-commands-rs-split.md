## 二、目标架构

### 7 个子模块 + 一个 slim facade

```
crates/nini-tui/src/commands/
  mod.rs            ← 重新导出（保留 crates::commands 路径）
  registry.rs       ← CommandId + CommandDef + REGISTRY + by_name + complete
  parse.rs          ← parse() (input → (CommandId, String))
  result.rs         ← CommandOutcome + CommandResult
  dispatch.rs       ← dispatch() — 28 个 match arm 拆为 fn
```

## 四、风险与缓解

### 风险 1：`dispatch()` 内部共享 helper 函数

`render_transcript_html()` / `entry_legacy_message()` 等是 dispatch() 调用的私有 helper。拆分时要把它们也提到独立模块。

**缓解**：在 Phase 1.5 就把 html_export 拆出去，dispatch() 改为 `html_export::render(...)` 调用。

### 风险 2：循环引用

`mod.rs` re-exports 所有子模块。如果子模块互相 use 会编译失败。

**缓解**：
- `registry` 不依赖任何其他 commands/ 子模块（纯数据）
- `result` 同上
- `parse` 依赖 `registry`（by_name）
- `dispatch` 依赖 `registry`, `result`, `status_lines`, `html_export`
- 依赖方向单向：dispatch → result/registry/status_lines/html_export → 无依赖

### 风险 3：测试覆盖增加导致回归发现

dispatch() 拆为 28 个 fn 后，每个 fn 都可以单测。某些历史 bug 会被发现。

**缓解**：每个新加的测试要写"已通过的最小 case"——保证不引入新 bug。

### 风险 4：commands/ 子目录的路径兼容

Rust 2018+ 不需要 `mod.rs`，但用 `mod.rs` 更显眼。其他 crate 还在引用 `crate::commands::xxx`（lib.rs re-exports）。

**缓解**：`pub use` 重导出 + lib.rs 不变 → 外部 API 完全兼容。
