## 2. 可行性评估（初步结论）

**已核实背景**：nini 为 Pi 的 clean-room Rust 重写（v1.0.1，`/home/jin/nini`，8 crate workspace），agent loop 单层折叠；硬上限 MAX_TOOL_ITERATIONS=50、DEFAULT_MAX_PARALLEL_TOOLS=8、max_tokens=8192、重试 3/500ms（当时的口径；现在的退避基数是 2000ms，见 `DEFAULT_RETRY_BASE_MS`，v1.0.3 起）；`agent_hooks.rs` 已预留 M2 `before_execute`/`after_execute`（Tool trait），当前仅 M1 上下文钩子；`nini-tools/src/mutation_queue.rs` 串行化文件写操作（变更/写管线）；nini 无 subagent、无后台/定时器、无 extension 运行时、无危险命令硬闸，已有 fixtures/conformance 测试（66 tests，oracle=真实 Pi 源码）；现有 72h 断点计划（`plan.md` + `docs/plans/long-task-72h-continuity-*`）进行中，含 4 处断点 D1–D4，约束为不改压缩/max_iterations/依赖、禁止为通过而编辑既有测试；方案来源为概念页 `concepts/agent-quality-engineering-constraint-2026-11.md`（五层体系、三禁例、先拦截后自动合并、验证为瓶颈、指标），评估结论为「质量左移 / 效率增益」而非算力/吞吐增益，能否变快取决于「门在合并/发版、验证局部化、规则先精简」。

**组件与落点映射表**：

| 方案层 | 方案含义 | 落点（文件或模块级） | 依赖 | 成本 |
| --- | --- | --- | --- | --- |
| ① 静态约束固化层 | 仓库即最强 prompt：规则固化质量约束 | 仓库规则与文档层，配合 `agent_hooks.rs` M1 上下文钩子 | 仓库既有文档与钩子基础设施 | 低 |

**可行性初步结论**：核心可落点（静态约束门 + 变更管线拦截）成本低、依赖低、可行性高；验证层仅局部化可行（全局形式化、每次红队均不可行），可降级为局部形式化 + 自实现独立运行；外围红队需自实现独立运行/独立 run，可行性中等；净性能增益为效率型（正收益），引入不当会拖慢。

**诚实标注**：本节为可行性评估结论，属方案评估而非代码实现；落点限定于已核实事实，需定位处标注「待代码定位」，不作已实现事实。

## 3. 范围（In scope / Out of scope）

**In scope**：

- 拦截门（变更/合并通道：`mutation_queue` 变更管线，或 `agent_hooks.rs` 的 M2 `before_execute`/`after_execute`，写工具前跑约束检查，不通过拒绝/回退，坏改动不进主干）

**Out of scope**：

- 修改现有 72h 断点修复（D1–D4 的实现）；与 72h 计划正交，不破坏
- 重构 agent loop、改压缩算法、改 `max_iterations` 语义、改依赖（clean-room 边界）
- 修改 CHANGELOG / README（除非随版本发布同步）

## 5. 风险与反效果（映射到 nini 具体风险）

本方案属「质量左移/效率增益」，收益取决于门设在合并/发版、验证局部化、规则先精简；不当引入检查会拖慢执行。结合 nini 实际能力（无 subagent、无扩展运行时、无危险命令硬闸，外围红队需自实现独立运行），主要风险与反效果如下：

① 门放进热路径（agent loop 每次 turn 跑检查）
- 风险点：把约束检查放进 agent loop 的每次 turn。
- 为什么会拖慢或成负收益：每次 turn 增加延迟与 token 开销，抵消效率增益。
- 缓解措施：门只放合并/发版通道，不进 agent 执行热路径。

② 全局形式化验证
- 风险点：对全部模块做全局形式化验证。
- 为什么会拖慢或成负收益：验证规模随代码膨胀，成本爆炸，超出成本承受。
- 缓解措施：仅对高风险模块做局部形式化验证。

③ 每次改动跑外围红队
- 风险点：对每次改动都跑外围红队。
- 为什么会拖慢或成负收益：等待时间累积、单次成本上升，抵消效率增益。
- 缓解措施：发版门按需跑红队，而非每次改动强制跑。

④ 规则过宽误报
- 风险点：规则过宽，对正常改动误报拦截。
- 为什么会拖慢或成负收益：误报导致失败轮次增加、返工，降低效率。
- 缓解措施：先落实核心 R1–R4 规则，阈值从宽到严，先用 conformance 回归验证不误报。

⑤ nini 无 subagent，外围红队需自实现
- 风险点：外围红队依赖内置 subagent，但 nini 无 subagent、无扩展运行时。
- 为什么会拖慢或成负收益：无法用内置 subagent 支撑红队，只能自实现，带来额外实现成本与不确定性。
- 缓解措施：用独立进程/独立 run 自实现外围红队，不依赖内置 subagent。

⑥ 与 72h 断点计划并发改动
- 风险点：与进行中的 72h 断点计划（D1–D4）并行改动，互相覆盖或干扰。
- 为什么会拖慢或成负收益：替换不精确会破坏既有断点修复，引入新问题，影响交付连续性。
- 缓解措施：精确替换、不覆盖他人改动；新增门须带回归测试，先跑回归验证不误报。

## 6. 验收标准（AC1–AC8，具体可检验）

AC 为待实施验收口径，需在实施后验证。

- AC1 约束门能拦截 R1–R4 坏写法，且放行正常改动：用既有 fixtures/conformance 测试（66 tests，oracle=真实 Pi 源码）回归，证明不误报、坏改动被拦。
- AC2 变更管线在写工具前执行约束检查，不通过则拒绝/回退，坏改动不进主干：构造坏改动用例，验证检查被拦截且主干未被污染。
- AC3 功能地图转化为功能级可执行验证清单：逐条真实执行、产出验证输出，非自报通过。
- AC4 局部形式化验证仅覆盖指定高风险模块，并产出局部验证产物：指定模块清单与验证产物一一对应。
- AC5 发版门红队以独立运行实现，能产出用例与缺陷修复（或至少用例生成）：独立进程运行，产出用例清单，缺陷可修复闭环。
- AC6 质量指标（拦截命中率/回退率/无效轮次）可记录对比：建立基线，实施前后对比并留档。
- AC7 不破坏 D1–D4 断点修复，既有构建与测试全绿（正交）：全量回归通过，D1–D4 修复不受影响。
- AC8 性能影响可控：核心改动不引入显著延迟与无效轮次，经回归指标验证无显著退化。
