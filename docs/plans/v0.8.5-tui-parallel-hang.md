# v0.8.5 — TUI 并行读卡死深度调研 + 修复计划

> **作者**：深度调研 by code analysis
> **日期**：2026-09-30
> **触发**：用户在 nini TUI 里让 pi-harness 并行读 14 个 docs 文件后 TUI 卡死
> **基于**：v0.8.4 (commit `2362f39`)
> **状态**：Draft，待评审

---

## 0. 复现情况

用户在 `nini` TUI 中输入：
> "现在让我并行读取所有的规划文档。"

pi-harness / 内置 LLM 在**一个回合内**发起 **14 个并行 `read` 工具调用**，
目标包括 `CHANGELOG.md` (1067 行 / 43 KB)、`docs/plans/*.md` 等大文件。

观察到的现象（截图）：
- 14 个 `read` 全部显示 `✓ Took 0ms`（已完成）
- 状态栏仍为 `nini idle` + `(anthropic) test-model`
- 用户后续键入 `▸ read {"path":"/home/jin/nini/CHANGELOG.md"}` 无法触发响应
- TUI 显示**卡死**（键盘无反应、画面不再刷新）

---

## 1. 根因分析（按严重性排序）

### 🔴 P0 — `sink_notify` 错配：agent 唤醒 runtime 的机制完全失效

**位置**：
- `crates/nini-tui/src/runtime.rs:1397-1407` — `submit_user_input` 自己 `Arc::new(Notify::new())`
- `crates/nini-tui/src/runtime.rs:1631` — 把这个 Notify 传给 `AgentSink::new`
- `crates/nini-tui/src/runtime.rs:342-344` — 运行时循环在**每次迭代**又 `Arc::new(Notify::new())` 创建**另一个** Notify
- `crates/nini-tui/src/runtime.rs:498-501` — `select!` 只听**本地这个** Notify

**Bug 链路**：

```
submit_user_input (line 1397)
    └─> submit_user_input_inner(sink_notify = Arc::new(Notify::new())  ← Notify #1
            └─> AgentSink::new(shared, sink_notify#1)
                  └─> agent 推事件 → self.notify.notify_one() → Notify #1

runtime loop (line 263)
    └─> let sink_notify = Arc::new(Notify::new())                      ← Notify #2
          └─> select! { sink_notify.notified() => ... }                 ← 只听 Notify #2
```

`Notify#1` 和 `Notify#2` **两个不同的 Arc**。
agent 调用 `Notify#1.notify_one()` 时，runtime 还在等 `Notify#2.notified()` → 通知丢失。

**后果**：
- v0.7.4 引入的"事件级 redraw"机制**完全失效**
- runtime 只在以下时刻重绘：
  - 50ms `tick`（动画 tick）
  - 25ms `editor_poll_tick`
  - 用户按键
  - `done_for_select`（agent 结束）
  - 主题变更
- agent 高频推事件时，UI 看到的状态**最多落后 50ms**

**为什么 v0.7.4 没被 e2e 测试抓到**：
`crates/nini-tui/tests/agent_wire_e2e.rs:531` 的 `concurrent_sink_pushes_dont_panic` 只测
"推 100 个 chunk，最终 state 是否齐了"，**不测"是否及时唤醒 runtime"**。
functional 正确，但 timing 完全没验证。

**为什么触发卡死**：
14 个 read 在 <50ms 完成（都是 fs::read_to_string + small file）→ agent 立刻推完所有
ToolResult 事件并 Done。但 runtime 等下一个 50ms tick 才看见 Done 事件。在那之前
runtime 还在 select! 上等待一个**永远不会触发**的 Notify#2。期间：
- 锁竞争：agent 推事件时反复 `state.lock()`，runtime 在 tick 之后尝试
  `let g = shared.lock().unwrap()` 抢锁；高负载下 runtime 反复 lock-失败-重试
- 即便 runtime 抢到锁并 snapshot，`render_transcript` 要遍历全部 transcript
  lines（14 个 ToolResult，每个内部含完整 25KB 内容 → `render_tool_result` 重处理
  ANSI strip + auto_link + 8 行 truncation，每帧 14 × O(N)）

**修复方向**：
1. **A 方案**（最小）：runtime 循环**复用同一个 Notify**，把它通过 `submit_user_input`
   传给 AgentSink。删掉两个独立的 `Arc::new(Notify::new())`。
2. **B 方案**（推荐）：用 `tokio::sync::watch::channel` 或 `broadcast::channel` 取代
   per-submit Notify，runtime `select!` 订阅一条，agent 推一条。
3. **C 方案**（彻底）：runtime 不再 poll Notify，改成"在 select! 里用 `events.next()`
   + `done_for_select.notified()`"，因为 50ms tick 已经够用。

### 🔴 P1 — Agent 串行执行 tool_calls，没有真正并行

**位置**：`crates/nini-core/src/agent.rs:1040-1158`

```rust
let mut tool_results: Vec<ContentBlock> = Vec::new();
for tc in &tool_calls {           // ← 串行 for 循环
    let output = match tool { ... };
    yield AgentEvent::ToolResult { ... };
    tool_results.push(...);
}
```

**问题**：
- 模型一次发出 14 个 `read` tool_calls（parallel calls），nini **串行执行**
- 每个 read 虽然快（fs::read），但**累积 14 次**系统调用 + 14 次 Mutex lock
- 用户的"并行读"心智模型被打破：14 reads 看起来是并行的，但实际是串行的

**修复方向**：
```rust
use futures::stream::{FuturesUnordered, StreamExt};

let mut futures = FuturesUnordered::new();
for tc in &tool_calls {
    if abort.is_aborted() { ... return; }
    futures.push(execute_one_tool(tc.clone(), tool_registry, ...));
}
let mut tool_results = Vec::with_capacity(tool_calls.len());
while let Some(result) = futures.next().await {
    yield AgentEvent::ToolResult { ... };
    tool_results.push(result);
}
```

需要保证：
- `tool_registry.get(tc.name)` 的 lookup 是 `&self`（已经是）
- 每个 tool 的 `execute(args, ctx)` 已经签名是 `async` + `Send`（已经是）
- before/after hook 也都是 `async`（看 `agent_hooks.rs`）
- abort 检查需要放在每个 future 里（用 `tokio::select!` 在 future 内部）

**收益**：14 个 read 从 ~70ms 降到 ~5ms（取决于 IO 并发上限）

### 🟠 P2 — `AgentSink::push` 二次加锁 + 事件可能乱序

**位置**：`crates/nini-tui/src/runtime.rs:96-172`

```rust
pub fn push(&self, ev: AgentEventLite) {
    if let Ok(mut s) = self.state.lock() {       // Lock #1
        if let AgentEventLite::PhaseChanged(phase) = &ev {
            s.run_state.status = phase.clone();
        }
    }                                            // Release #1
    if let Ok(mut s) = self.state.lock() {       // Lock #2
        match ev { ... }                         // 真正写
    }
    self.notify.notify_one();
}
```

**问题**：
- 每次 push 加锁 2 次（额外的 syscall + cache miss）
- 两个锁之间窗口期，其他线程（包括 runtime 的 snapshot）可以插队
- 并发 push 时 `PhaseChanged` 和实际事件可能被分割处理 → 状态错乱

**修复**：合并到一个锁块里。

```rust
pub fn push(&self, ev: AgentEventLite) {
    let result = {
        let Ok(mut s) = self.state.lock() else { return; };
        if let AgentEventLite::PhaseChanged(phase) = &ev {
            s.run_state.status = phase.clone();
        }
        match ev {
            AgentEventLite::TextDelta(text) => s.push_assistant_raw(text),
            ...
        }
    };
    let _ = result;  // avoid holding lock during notify
    self.notify.notify_one();
}
```

### 🟠 P3 — Tool result 完整内容长期占据 transcript 内存 + 渲染

**位置**：`crates/nini-tui/src/state.rs:1245-1260`

```rust
pub fn push_tool_result_raw(&mut self, ok: bool, content: impl Into<String>, ...) {
    self.transcript_state.lines.push(TranscriptLine::ToolResult {
        content: content.into(),     // ← 完整 25KB 一直存在
        ...
    });
}
```

`TranscriptLine::ToolResult.content` 永久持有原始内容。
即使渲染时只显示前 8 行 + 200 字符/行（`crates/nini-tui/src/rich.rs:223-238`），
完整内容依然驻留在 `state.transcript_state.lines`。

**问题**：
- 14 个 25KB tool result = 350KB 永久内存占用
- 每次重绘都要遍历整个 content（`strip_ansi` + `auto_link` + `lines()`）即使只显示头 8 行
- 没有上限 → transcript 越来越大

**修复**：
- 在 `push_tool_result_raw` 里立刻截断 content 到 `TOOL_RESULT_PREVIEW_MAX_BYTES`
- 渲染时不再需要 `linked.len() > TOOL_RESULT_PREVIEW_MAX_BYTES` 路径
- 收益：单 frame render work 从 O(N_total) 降到 O(N_visible)

### 🟡 P4 — `auto_link` 双重 chars().next() 调用

**位置**：`crates/nini-tui/src/hyperlink.rs:88-99`

```rust
out.push(s[i..].chars().next().unwrap());
i += s[i..].chars().next().unwrap().len_utf8();   // ← 同一个调用做两遍
```

每次非 URL 字符调两次 `chars().next()`，每次都重新做 UTF-8 解码。

**修复**：
```rust
let mut chars = s[i..].chars();
if let Some(c) = chars.next() {
    out.push(c);
    i += c.len_utf8();
} else {
    break;
}
```

收益：tool result 渲染 CPU 减半（不显著但零成本）。

### 🟡 P5 — Transcript 无硬上限 + 缺 auto-compaction 触发点

**位置**：`crates/nini-tui/src/state.rs`、`crates/nini-core/src/agent.rs`

- `transcript_state.lines: Vec<TranscriptLine>` 没有最大行数限制
- `should_auto_compact` 只在 `submit_user_input` 时检查
- agent loop 内部不检查 → tool calls 灌进 context 后无法在中间触发 compaction

**修复**：
- 加 `TranscriptState::MAX_LINES = 500`（v0.5→v0.7 都是 0 限制）
- agent loop 里在每个 tool_call 完成后检查 `messages.iter().map(|m| tokens).sum() > context_window * 0.8`
- 超阈值则 yield `AgentEvent::CompactionNeeded`，让 TUI 决定是否触发

## 2. 修复优先级与计划

### Sprint 1 — 立刻止血（v0.8.5）

| 优先级 | 任务 | 文件 | LOC 估 |
|--------|------|------|--------|
| P0-A | 修复 sink_notify 错配（用同一个 Notify） | `runtime.rs` | ~10 |
| P2 | 合并 `AgentSink::push` 双锁 | `runtime.rs` | ~10 |
| P3 | `push_tool_result_raw` 立即截断 content | `state.rs` + `rich.rs` | ~15 |
| P4 | `auto_link` 单次 `chars().next()` | `hyperlink.rs` | ~5 |
| 测试 | 加 `sink_wakes_runtime` e2e（mock agent 推事件 → assert runtime 立即 redraw） | `tests/` | ~60 |

**总估**：~100 LOC + 60 LOC 测试 = 160 LOC

### Sprint 2 — 性能优化（v0.8.6）

| 优先级 | 任务 | 文件 | LOC 估 |
|--------|------|------|--------|
| P1 | 改 agent tool_calls 为 `FuturesUnordered` 并行 | `agent.rs` | ~50 |
| P5 | transcript MAX_LINES + agent loop 内的 compaction check | `state.rs` + `agent.rs` | ~60 |
| 测试 | 14 reads 并行执行的 e2e（mock tools + assert 完成时间） | `tests/` | ~80 |

**总估**：~190 LOC + 80 LOC 测试

### Sprint 3 — 架构清理（v0.9.0）

- 把 `SharedState` 从 `Arc<Mutex<AppState>>` 改成 `Arc<RwLock<AppState>>` 减少读路径锁竞争
- AgentEvent → AgentEventLite 转换改用 `tokio::sync::broadcast` channel（取代 per-loop Notify）
- TranscriptLine 增加 `Arc<str>` 字段，避免每次 clone
