## 0. 调查方法

| 手段 | 说明 |
|---|---|
| `cargo clippy --workspace --all-targets` | **0 warning** —— 这本身是问题，见 §H7 |
| `cargo test --workspace` | **937 / 937 全过** —— 同样不能作为验收信号，见 §H7 |
| 全符号交叉引用 | 对每个 `pub fn` / `pub type` / `pub mod` 在全仓 `grep` 出现次数；`≤1` 即只出现在定义处 |
| 死依赖对账 | `Cargo.toml` 声明 vs `grep "<crate>::"` 实际引用 |
| 空壳扫描 | 搜 `_arg` 形式的未使用形参、无副作用的 `Ok(())`、`_ => None` |
| 承诺面对账 | 把 README / `--help` / 状态栏文案 / 命令输出里对用户的每条承诺，反向验证代码 |

**为什么必须用交叉引用而不是 clippy**：本项目所有跨 crate 条目都是 `pub`，而 `pub` 项**不触发 Rust 的 `dead_code` lint**（`[workspace.lints.rust] missing_docs = "allow"` 进一步放宽）。所以「clippy 零告警」与「零死代码」在本仓库**不等价**。

### 0.1 对上一轮调研结论的两处自我纠正

同一次调研里我犯了两个错，必须记录在案 —— 它们直接决定了本计划的 §H1 和 §H6。

`nini-core/src/project_trust.rs:99-119` 全部是空壳：

```rust

pub fn save(&self, _path: &Path) -> Result<(), io::Error> { Ok(()) }            // 永不写文件
pub fn get(&self, _key: &str) -> Option<TrustDecision> { Some(self.decision…) } // 忽略 key
pub fn clear(&mut self, _cwd: &str) {}                                          // 空
pub fn default_path() -> Option<PathBuf> { Some(".pi/agent/trust.json") }       // CWD 相对！
```

而且 `check()` —— 整个信任**执行闸门** —— **零生产调用点**。所以 `/trust` 是第 5 个「报成功但什么都没做」。

**纠正 2：漏掉了本次最严重的一个 P0。** 上一轮完全没查 CLI 层的 flag 消费情况，因而漏掉了 skills 注入与 17 个被丢弃的 flag（见 P0-1 / P0-3）。

**教训**：抽样验证 28 个命令中的 3 个，结论就错了 1 个。本计划 §5 的 Phase 0 必须做**全量承诺面对账**，不能抽样。

### 0.2 Phase 0 对账结果（已完成，2026-10-05）

全量对账后，结论清单有 **3 处修正 + 1 项新增**：

**修正 A —— P0-3 的 17 个数字是对的，但分类要更细。** `main.rs:270-306` 其实已经有一个诚实机制：6 个 session 相关 flag（`--continue-session` `--session-id` `--no-session` `--name` `--fork` `--session-dir`）会被收进 `ignored` 向量并打印 `ignoring …: TUI session persistence is not implemented yet`。真正**静默丢弃**的是另外 17 个。36 个 flag 的最终账目：**13 个生效 / 6 个已警告 / 17 个静默丢弃**。

顺带发现修复的现成范式，`main.rs:270-276` 已经把理由写清楚了：

> *"v0.9.0: these were all `_: _` in the destructure above, i.e. accepted, documented in `--help`, and then dropped on the floor. … Silently ignoring a flag is worse than refusing it."*

P0-3 的 B 类处理方案（移除 flag）应复用这套“宁可拒绝、不可静默”的措辞，而不是自创新口径。

**修正 B —— `/settings` 也不一致（新增到 P1-5）。** `cmd_settings`（`dispatch.rs:67`）自己注释写着 *"mock until real settings UI is wired"*，输出标题是 `Settings (read-only)`。但 `SettingsSelector` 真实存在且 `runtime.rs:1684` 监听 `open_selector:settings` —— **即选择器实现了，但 `/settings` 不打开它**（只能通过某个键位触发）。属于“承诺与实现两张皮”。

**修正 C —— 6 个命令的 README 状态标注再次确认。** 全量读实现后：`/resume` 真实现（还带诚实的 skipped-lines 提示，值得肯定）；`/new` 真实现；`/export` 真写盘；`/changelog` 真解析；`nini info` 输出诚实。而 `/model` `/thinking` 确认**不落盘** —— `set_default_model` 只改内存（`settings.rs`），只有 `/scoped-models` 调了 `flush()`。

**新增 P1-7 —— 状态栏 context 进度条与 `/status` 的 context 行永不渲染。**
`set_status_bar_usage`（`state.rs:1287`）是本报告 25 个死 `pub fn` 之一，它是 `context_window` / `context_used` 的**唯一写入者**（`state.rs:1134` 初始化为 0）。因此：

- `render.rs:401` `if context_window > 0` **恒为假** ⇒ 状态栏进度条不出现
- `status_lines.rs:35` 同样的判断 ⇒ `/status` 永远只有 6 行，**永远没有 context 百分比**
- 而 `status_lines.rs:73` 的测试**手动赋值** `context_window = 1000` —— **测试自己把死路径掩盖了**（与 H7 同型）

这是 §H7「测试通过率不是质量信号」最干净的一个实例：测试是绿的，功能是死的，而且**绿的测试正是它死的原因**。

**证据链**：

### P0-2 项目信任（二选一，禁止半修）

**方案 A（推荐）— 完整实现**
- `save`/`load` 用 serde 真读写 JSON；`get` 查真实 `cwd_map`；`clear` 真删 key
- **路径统一到 `~/.pi/agent/trust.json`**：`default_path()` 当前的 `.pi/agent/trust.json`（CWD 相对）与 `runtime.rs:815-819` 手工拼的 HOME 路径不一致，两处写的是**不同文件**
- **在工具执行路径调用 `check()`** —— 这是唯一让信任生效的动作
- 加逃生阀 `NINI_TRUST=off`，避免 `Distrust → Deny` 真阻断后用户无法自救

**方案 B — 整块删除**（命令 + 选择器 + 模块 + README）

**行为变更警告**：`Distrust → Deny` 一旦真正生效，会**阻断用户正在进行的工具调用**。这是本计划里唯一有用户可感知破坏性的改动，必须独立 PR + 独立版本。

### P0-3 17 个被丢弃的 flag（拆两类处理）

> **Phase 0 修正**：36 个 flag 的账目是 **13 生效 / 6 已警告 / 17 静默丢弃**。
> `main.rs:270-306` 已有诚实机制覆盖 6 个 session flag；真正静默的是下列 17 个。
> `main.rs:270-276` 已写明理由：「*Silently ignoring a flag is worse than refusing it.」**B 类移除请复用此措辞。**

`main.rs:244-260` 用 `_` 丢弃：`system_prompt` `append_system_prompt` `thinking` `tui_mode` `approve` `offline` `verbose` `export` `skill` `no_skills` `prompt_template` `no_prompt_templates` `theme_file` `no_themes` `extension` `no_extensions` `no_context_files`

`AppConfig` 里已有先例注释记录了这个 bug 模式（`--api-key`，v0.9.0 修复）—— **团队已知晓，但只修了 1 个**。

|---|---|---|---|
| **A 类**（接线即可） | `thinking` `no_skills` `no_prompt_templates` `no_themes` `verbose` `tui_mode` `theme_file` `offline` | 接线进 `AppConfig` | < 20 行/个 |

### P0-4 `/copy`

## 4. P1 关键设计决策

### P1-2 主题热重载（零新增依赖）

`notify = "6.1"` **已在 nini-tui 依赖里、零使用** ⇒ 实现成本不含依赖引入。但必须修两处设计错：

1. **监听目标错**：现签名收 `cwd`，而主题在 `~/.pi/agent/theme.json` 与 `./.pi/theme.json`（`theme.rs:8-9`）。应监听这两个具体路径。
2. **返回值错**：返回 `Option<PathBuf>`，而 `runtime.rs:353` 的 `let _watcher = …` 本意是**持有 watcher 防止 drop**。返回 PathBuf 意味着即使实现了 watcher 也会立刻析构。应返回 `RecommendedWatcher`（或 box it）。

### P1-3 `/tree` —— 明确**不做**三层实现

`/tree` 断在三层：

| 层 | 状态 |
|---|---|
| ① 数据层 `parent_id` | `state.rs:1426,1432` 两处生产调用**恒传 `None`** ⇒ 磁盘上根本没有树 |
| ② 模型层 `SessionTree` | 5 个方法恒返回空 |
| ③ 视图层 `TreeSelector` | 平铺列表，**完全忽略 `parent_id`**；`summarize_at` 恒 `None` |

**决策：不实现。** 因为 `/fork`（`dispatch.rs:520`）不产生分支会话文件 ⇒ 即使三层全实现，树**恒为一条直线**。边际收益为零。

改为让 `/tree` **说真话**：如实报告 N 条线性记录，并明确标注「分支未实现」。见 §H12 的 UX 折中。

### P1-1 `/debug` —— 需先决策（阻塞 P2-6）

`debug_logging`（`state.rs:1037`）只有 3 处赋值、**0 个读取**。二选一：

- **A**：接最小文件日志（`~/.pi/agent/log/nini.log`），`tracing` 依赖有了归宿
- **B**：让 `/debug` 诚实输出「日志系统未接线」

**此决策不定，P2-6 无法执行**（`tracing`/`tracing-subscriber` 留还是删悬空）。见 §H5。

## 7. 计划漏洞自查

> 这一节是本计划的一部分，不是附录。**每一条都是对本计划自身的攻击面。**

### H1 🔴 本次调研可能仍是错的（最大漏洞）

§0.1 已自证：抽样 3 个命令就错 1 个（`/trust`），并因此漏掉了 P0-1 这个更严重的问题。**因此不能假设 P0-1/P0-2 已完整。**

**缓解**：Phase 0 必须把 README + `--help` + 状态栏文案 + 命令输出里的**每一条**对用户承诺逐条 grep 反查代码，产出对账表，再决定本清单是否补项。
**残余风险**：无法排除仍有一批「没人测过、没人写进 README、但确实无效」的功能。只能靠 Phase 0 尽量收敛。

### H2 🔴 P0-1 会引入回归，且当前无法证明修复有效

注入 skills 会改变**每一次请求**的 system 内容 ⇒ 影响 prompt cache、token 计费、模型行为。而 937 个测试**没有任何一个断言 system prompt 内容** ⇒ 改完也无法证明。
**缓解**：**先写一个断言 skills 出现在 system prompt 里的失败测试，红→绿**，再改实现。这是本计划唯一的 TDD 强制项。

### H3 🟠 P1-4 会重写 P0-1 的代码，低估工期

`RunConfig` 在 `app.rs:112` 一次性构建后被 `move` 进 driver 闭包（`app.rs:122`）⇒ 运行时无法替换。若 Phase 2 与 Phase 6 一起做，P0-1 的注入点会被二次改写。
**缓解**：明确 P1-4 独立成阶段并接受它会动 Phase 2 的代码；Phase 2 的注入点设计要预留可替换形态（把 `skills_prompt` 收进一个可变的 `Arc`）。

### H4 🟠 删 `--extension` 与删 `nini-ext` 未绑定

若 P2-1 删 crate 而 P0-3 留 flag（或反之），会出现「flag 没了 crate 还在」的不一致。
**缓解**：§5 已把两者放进同一 Phase；评审时作为**单点决策**检查。

### H5 🟠 P1-1 二选一未决 ⇒ P2-6 悬空

`tracing`/`tracing-subscriber` 的去留完全取决于 P1-1 选 A 还是 B。
**缓解**：把该决策上移到 Phase 0，与「保留假象 vs 撤掉承诺」判据一并拍板。

### H6 🔴 死代码删除可能重犯 v0.8.4 / v0.8.9 的「误删」错误

`docs/plans/v0.8.9` 记载：`/hotkeys` 在 v0.8 重构中「left this as a stub」，最后是**恢复实现**而不是删除。`registry.rs::score()` 也带 `#[allow(dead_code)]` 且注释写「v0.8.4 restored from a refactor that silently dropped it」。

⇒ **「当前零调用」不等于「不该存在」**，很可能是重构回归或未写测试。
**缓解**：P2-5 逐个 `git log -S<fn名>` 核查历史。**在核查完成前不删任何 `pub fn`**，只加 `#[allow(dead_code)]` + tracking issue。宁留勿误删。

### H7 🔴 「937 测试 + 0 clippy」是自欺信号

P0 全部存在，而两个门禁都全绿。`pub` 掩盖死代码是**结构性**的，不是一次性的。
**缓解**：
1. 验收标准改为**行为断言测试**，不看总数
2. 新增 CI 门禁：禁止新增零调用点的 `pub fn`（`cargo +nightly -Z dead-code` 或 `cargo-udeps`），否则下一轮还会长回来

### H8 🟠 17 这个数字可能不全

只清点了 `main.rs` 的 destructure。`Args` 可能还有子命令（`cmd`）分支下的独立 flag 未纳入。
**缓解**：Phase 0 用脚本对账「clap 声明数 vs 实际消费数」，覆盖子命令路径。

### H9 🟠 B 类 flag 移除是破坏性变更

虽然是 no-op，但用户可能已在脚本里写 `nini --approve …` 并**以为它在工作**。移除后脚本报「未知参数」而失败 —— 这其实是暴露问题的好事，但属破坏性变更，需 CHANGELOG 明确 + major 语义。

### H10 🟠 多数项无法用测试证明「用户不再被骗」

P0-3/P0-4/P0-5 的本质是「让假象消失」，测试只能证明新行为，不能证明用户不会再被误导。
**缓解**：每个 P0 项配一个**可复现的手工验证脚本**（参照 v0.8.9 计划的 TestBackend 实拍 / `/proc` 实测风格），写进计划的验收栏。

### H11 🟠 P0-1 的优先级依赖一个未确认的产品定位

若 nini 定位是「CLI 单次任务工具」而非「Pi 替代品」，skills 的价值取决于用户是否用 TUI。README 写 "Drop it in alongside Pi" ⇒ 支持 P0-1 成立，但**这个定位从未被显式确认**。
**缓解**：评审时由项目所有者拍板定位；若定位为 CLI 工具，P0-1 降为 P1。

### H12 🟡 `/tree`「说真话」的 UX 折中没定

如实输出「N 条线性记录，分支未实现」对 Pi 用户是否可接受？更激进的做法是把 `/tree` 从 28 命令中移除 —— 但那会破坏兼容性。
**缓解**：保留命令 + 明确标注为**折中方案**，评审时确认。

### H13 🟡 计划缺少「回滚」设计

P0-2 若走方案 A，`Distrust → Deny` 真阻断后，用户如何自救？只提了 `NINI_TRUST=off`，未验证该逃生阀本身不会被同一 bug 影响。
**缓解**：逃生阀走与 `ProjectTrustStore` **完全独立**的读取路径（直接 `std::env`），不经过任何被怀疑的代码。

## 9. Phase 2 实施记录（P0-1，已完成）

**改动**：`app.rs` 抽出 `build_tui_run_config()` + `AppConfig::no_skills` + 状态栏单一数据源；`main.rs` 接线 `--no-skills`。
**测试**：944 → **950**（+6）。clippy 0 warning。

### 9.1 TDD 已实际执行（不是声称）

按 §H2 要求先写失败测试。为避免「测试一写出来就绿」的假 TDD，做法是：

1. 先抽出接缝 `build_tui_run_config`（行为不变）
2. 写测试 → 绿
3. **把修复临时回退成 v0.9.1 的 `""`** → 重跑
4. 观察：**3 个测试变红，其余 3 个仍绿**

```
bug injected
test …::empty_project_yields_no_skills_block_and_no_panic ... ok
test …::no_skills_flag_suppresses_the_block ... ok
test …::skills_fix_preserves_the_working_directory_hint ... ok
test …::skills_visible_to_user_match_skills_in_prompt ... FAILED
test …::status_bar_count_and_prompt_contents_agree_under_both_flag_states ... FAILED
test …::tui_system_prompt_actually_contains_the_skills_block ... FAILED
test result: FAILED. 33 passed; 3 failed;
```

不变绿的三个都**不依赖**该修复，说明断言是针对性的而非宽泛的。

### 9.1.1 收尾时又抓到一个假测试（重要）

一致性测试首版写成：

```rust
let status_count = on_disk;        // 硬编码字面量
assert_eq!(status_count, in_prompt);
```

这是**同义反复** —— 左边不来自被测代码，无论生产代码烂成什么样它都绿。**本报告批评的就是这类「看着绿、什么都没证明」的测试，而它出现在我自己的新测试里。**

改为直接断言 `build_tui_run_config` **真实返回的**计数，并再次做注入实验验证：变红测试从 **2 个增加到 3 个**（新增的那个正是重写后的一致性测试）。教训：**测试必须从被测函数取值，测试里自己造的常量一律无效。**

同时把函数签名从 `-> RunConfig` 改为 `-> (RunConfig, usize)`，让「状态栏数字」与「prompt 内容」**强制同源**，skills 目录每次启动从读 3 次降为 1 次。

### 9.2 实施中发现的新问题（重要）

**我的修复自己引入了同类 bug。** 首版只改了 prompt，状态栏仍独立 `load_skills` 算自己的数。结果 `--no-skills` 下会出现：

> 状态栏：`loaded 3 skills` ／ prompt：**0 个 skill**

—— 把同一个谎话搬到了新位置。`skills` 在一个函数里被读**三次**（v0.5 那次丢弃、`build_tui_run_config`、状态栏），三个独立数据源 = 三次可能不一致的机会，而不一致正是本版本要消灭的病根。

**修正**：`skills_in_prompt` 成为单一数据源，由 `run_tui` 算出后**作为参数传入** `run_tui_bootstrap`（不改 `nini_tui::run` 的签名），并加测试 `status_bar_count_and_prompt_contents_agree_under_both_flag_states` 锁住该不变量（两个 flag 状态下均验）。

### 9.3 实施中的技术细节

- **接缝位置**：`build_tui_run_config` 抽在 `app.rs`（`pub(crate)`），因为 `run_tui` 是需要 TTY 的 `async fn`，里面的逻辑**任何测试都调不到** —— 这就是当初这个 bug 能躲过 937 个绿测试的根因。
- **不动 `nini_tui::run`**：初版误把参数加到了 `run_tui_inner`（= `nini_tui::run`）上，会改跨 crate 公开签名；已改为传给自己的 `run_tui_bootstrap`。
- **代价可接受**：`format_skills_for_prompt` 只输出 name/description/location 的 XML 索引，**不注入 SKILL.md 正文**，token 成本极低。
- **端到端确认**：`--help` 已含 `--no-skills`；`nini --no-skills --provider fixture -p hi` 退出码 0；`nini info` 在含 `.pi/skills/` 的目录下正确报出 `1 loaded`。

THE_ANSWER_TEXT                                    ← 真的输出了

### 10.1 两处额外修正（连带的真 bug）

1. **`/logout` 重复项**：`openai` / `openai-responses` / `openai-compat` 同映射 `OPENAI_API_KEY`，裸 `/logout` 会打印 3 次。已用 `BTreeSet` 去重，**已加回归测试**。
2. **删除死函数 `clipboard::read_image`**（恒返 `None`，零调用者；图片侧 `image_paste.rs` 直接用 arboard）。

### 10.2 实施中发现的细节（值得记入设计约束）

**不要用 `std::env::remove_var`。** 修 `/logout` 时最顺手的做法是直接 `remove_var`，但：

- TUI 是多线程 tokio 运行时，`remove_var` 与其它线程的 `var_os` 构成**数据竞争**（unsound，不只是风格问题）
- edition 2024 已直接禁止该 API；本项目是 2021，所以**编译器不会拦你** —— 换 edition 时会突然编译失败

因此走“检测 + 给出可执行 shell 命令”路线。代码里已写明，避免下一个维护者踩坑。

**新增的测试接缝**：`classify_copy(msg, Result)` 是纯函数，两个分支都能在无剪贴板的 CI 上确定性测试。这是这两个 P0 能存在 937 个绿测试下而不被发现的**根因** —— 原来的代码没有可测接缝。
