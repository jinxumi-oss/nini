## 3. 发现的问题（按严重度排序）

### 🔴 Critical 问题（导致功能完全不可用）

#### 问题 #1：openai-compat provider URL 双重拼接

**严重度**: 🔴 Critical — 整个 LLM 集成对端点带 `/v1` 的 provider 不可用

**重现**:
```bash
OPENAI_BASE_URL='https://m.aiio.chat/v1' nini --provider openai-compat --model MiniMax-M3
> 任意 prompt
```

**症状**: TUI 完全卡住 50+ 秒，无任何响应。模型选择器正常工作，但用户提交 prompt 后没有任何输出。

**根因**:
```rust
// crates/nini-ai/src/openai.rs (修复前)
let url = format!("{base_url}/v1/chat/completions");
```

当用户的 `base_url` 已经包含 `/v1`（如 `https://m.aiio.chat/v1`），代码会拼接成 `https://m.aiio.chat/v1/v1/chat/completions`，命中 HTML 404 页面而非 API。Agent 流一直等待永远不会来的 SSE 数据。

**发现方法**:
1. 直接 curl 验证：`https://m.aiio.chat/v1/v1/chat/completions` 返回 HTML，401
2. `https://m.aiio.chat/v1/chat/completions` 返回正常 JSON
3. 在 openai.rs 添加 eprintln，发现 chunk 是 HTML 而非 JSON

**修复**:
```rust
let url = format!("{base_url}{}/chat/completions",
    if base_url.ends_with("/v1") { "" } else { "/v1" });
```

3 个单元测试覆盖 OpenAI / OpenRouter / m.aiio.chat 三种 URL 约定。

**为什么这是 critical**: nini 的整个 LLM 集成对一个**最自然的 URL 配置**都失败。如果用户按 OpenAI 官方文档设置 base_url，会失败；只有按 nini 内部期望设置（不带 `/v1`）才工作。这是把整个产品定位（"OpenAI 兼容"）拆了的 bug。

**影响**: 所有用 m.aiio.chat、任何已经带 `/v1` 的 OpenAI-compat provider 的用户。

---

#### 问题 #2：Agent 流的 Err 事件被静默吞掉

**严重度**: 🔴 Critical — 任何 agent 错误用户都看不到

**重现**: 任何导致 `agent.run()` 返回 Err 的场景（网络错误、JSON 解析错误、auth 错误、provider 协议不匹配等）

**症状**: 用户提交 prompt 后 TUI 完全无响应，没有任何错误提示。"看起来什么都没发生"。

**根因**:
```rust
// crates/nini-cli/src/main.rs (修复前)
while let Some(ev) = stream.next().await {
    let lite = match ev {
        Ok(AgentEvent::TextDelta { text }) => ...,
        // ... 几个显式分支
        Err(_) => continue,    // ← 静默吞掉所有错误
        _ => continue,         // ← 静默吞掉所有未处理的 Ok 变体
    };
    sink.push(lite);
}
```

**修复**:
```rust
Err(e) => nini_tui::runtime::AgentEventLite::Error(
    format!("agent stream error: {e}")
),
Ok(other) => nini_tui::runtime::AgentEventLite::PhaseChanged(
    format!("agent: {other:?}")
),
```

这样用户至少能看到 `agent stream error: ...` 在状态栏或 transcript 里。

**为什么这是 critical**: TUI 在错误状态下变成"挂起"，用户没法区分"模型在想"和"出错了"。这违反了"任何状态都该被显示"的基本 UX 原则。

### 🟠 High 问题（严重但用户能恢复）

#### 问题 #3：`eprintln!` 调试输出泄漏到 TUI

**严重度**: 🟠 High — 用户看到大量内部调试字符串

**重现**: 任何一次 prompt 提交

**症状**: TUI 底部出现 `[submit_user_input] spawning agent for text='...'`、`[submit] input.text='...'` 等调试输出，与 footer 文字重叠。

**根因**: 之前为调试写入的 `eprintln!` 没清理：
```rust
eprintln!("[submit_user_input] regular path, text='{text}'");
eprintln!("[submit_user_input] spawning agent for text='{text}'");
eprintln!("[submit] input.text='{}' completion={} search={}", ...);
```

在 tmux（或大多数终端）里，stderr 不会被 alt-screen 隔离，会渲染到 alt-screen 内容里。

**修复**: 移除这 3 个调试 eprintln。保留事件错误、theme watcher 错误、session load 错误等合理的 eprintln（这些是罕见的、用户想知道的事件）。

---

#### 问题 #4：`AgentPhase` 没有 Display impl

**严重度**: 🟠 High — 状态栏显示 Rust Debug 格式

**重现**: 任何 compaction 或 retry 触发

**症状**: 状态栏显示 `Working { reason: "overflow", progress: None }` 而不是 `working` 或 `compacting:overflow`

**根因**: `AgentPhase` enum 没有 `Display` impl，CLI driver 用了 `format!("{phase:?}")`（Debug 格式）

**修复**:
```rust
impl std::fmt::Display for AgentPhase {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        match self {
            AgentPhase::Idle => write!(f, "idle"),
            AgentPhase::Working => write!(f, "working"),
            AgentPhase::Compacting { reason, progress } => {
                if let Some(p) = progress {
                    write!(f, "compacting:{reason} ({p}%)")
                } else {
                    write!(f, "compacting:{reason}")
                }
            }
            AgentPhase::Retrying { attempt } => write!(f, "retrying (attempt {attempt})"),
            AgentPhase::BranchSummary => write!(f, "branch summary"),
        }
    }
}
```

5 个单元测试覆盖所有 phase 变体。

### 🟡 Medium 问题（影响体验但不致命）

#### 问题 #5：状态栏不更新 `idle → running`

**严重度**: 🟡 Medium — 用户没法判断 agent 是不是在工作

**症状**: 提交 prompt 后，状态栏仍然显示 `idle`，不切到 `running`。看 transcript 区的提示是有的，但状态栏反应迟钝。

**根因**: 待查。snapshot 是在 loop 顶部取，应该反映新状态，但渲染似乎没及时更新。

**临时缓解**: 用户可以看 transcript 区有没有 prompt 来判断是不是 submit 了。

---

#### 问题 #6：MiniMax-M3 模型的 `<think>...</think>` 推理块泄漏到 transcript

**严重度**: 🟡 Medium — 用户看到模型的"内心独白"

**重现**: 用 MiniMax-M3 (用户的 LLM) 跑任意 prompt

**症状**: transcript 区显示 `<think>The user wants me to...</think>` 而不只是最终回答

**根因**: MiniMax-M3 的响应在 `delta.content` 里同时包含 reasoning（被 `<mm:think>` 标签包裹）和实际内容。nini 的 OpenAI parser 把所有 `delta.content` 都当 TextDelta 发出。

**修复方向**: 
- 加 `<think>...</think>` 标签剥离逻辑（在 provider 或 agent_hooks 层）
- 或者用 provider 的 `reasoning_content` 字段（如果存在）

**当前状态**: 未修复。需要确认是 MiniMax 专属还是其他 provider 也这样。

---

#### 问题 #7：模型选择器只显示 builtin 模型，不显示用户配置的模型

**严重度**: 🟡 Medium — 选了模型后实际 model id 仍然是 `test-model`

**症状**: 状态栏显示 `test-model`，但用户选了 `MiniMax-M3`。`AppState::model` 字段没有同步。

**根因**: `AppState::model` 是 bootstrap 时设的，model selector 切换的是 provider 的 model 字段，但状态栏显示的是 AppState.model 字段。

**影响**: 用户感觉选模型没生效。

## 5. 整体评估

### 5.1 优势（这次测试确认 OK 的部分）

- **TUI 渲染**: `/help`、`/hotkeys`、`/status`、model selector 都正常工作，输出排版清晰
- **slash 命令**: 28 个命令全部识别，autocomplete 工作
- **Ctrl+G 外部编辑器**: 正常工作（用 nano 编辑输入框，返回时 buffer 更新）
- **fixture provider 端到端**: 完全可用，能跑预定义的 demo 流程
- **JSONL session 兼容性**: v0.6.x 写的 session 用 v0.7.2 读没问题（v0.7.1 修了 ToolResult 丢消息 bug）
- **Test coverage**: 679 tests 通过，全绿

### 5.2 弱点

- **openai-compat provider 对 URL 约定脆弱**: 一个 `ends_with("/v1")` 检测就解决了，但需要文档化
- **错误状态对用户完全不可见**: 这是本次最大发现 — 任何失败都是"看起来在转"
- **Provider 协议细节泄漏到 UI**: `<think>` 标签说明 nini 假设所有 OpenAI-compat provider 都返回"纯内容"，但实际可能返回 reasoning + content

### 5.3 建议优先级

1. **立即 (v0.7.3)**: 修 #5、#7 — 状态显示相关的小修
2. **v0.7.4 / v0.7.5**: 修 #6 — `<think>` 剥离（用 provider 的 reasoning field）
3. **v0.8**: 重新设计 openai-compat 配置 — 让用户选 endpoint convention 而不是 auto-detect

## 8. v0.7.4 回归验证

在 v0.7.4 修复提交 (`8c7be21`) 之后重跑了同一个真实任务集，验证全部修复生效：

### 8.1 Fix #7 验证 — 状态栏显示真实模型

**之前**: `nini test-model | ~/nini | ⎇ main | idle ...`（启动时永远显示 `test-model`）

**v0.7.4**: `nini MiniMax-M2.7-highspeed | ~/nini | ⎇ main | idle ...`（显示实际模型）

**修复路径**: bootstrap 函数原本读 `s.provider` 先于 `s.model`，把 provider 名赋给 `state.model` 字段。修复后读顺序改为 CLI `--model` → `s.model` → `s.provider` → `"test-model"`。

### 8.2 Fix #6 验证 — `<think>` 标签剥离

**之前**: transcript 区显示 `<think>The user wants me to count from 1 to 5...\n</think>\n1, 2, 3, 4, 5`

**v0.7.4**: transcript 区只显示 `1, 2, 3, 4, 5`

**修复路径**: 在 `nini-ai/src/openai.rs` 加 `ThinkTagFilter`，状态机式地过滤 `<think>...</think>` 块。块可能跨 chunk 边界，所以维护一个小的 hold-back buffer 兜底。

**测试覆盖**: 10 个单元测试包括完整块剥离、跨 chunk 边界的开放/关闭标签、多个块、空 input、跨 chunk 边界的不可解析序列等。

### 8.3 Fix #5 验证 — TUI 在事件间重绘

**之前**: TUI 仅在 50ms tick / 用户输入 / agent 完成 时重绘。快 agent（<50ms 完成）从不显示中间状态（"Working"、"text delta"、"tool call"）。

**v0.7.4**: `AgentSink` 现在携带 `Arc<Notify>`，每次 `push` 调用都通知 runtime 的 select! 循环。runtime 在事件间重新 snapshot 并重绘。

**验证**: streaming 响应"Explain in 2 sentences why the sky is blue" 时，transcript 区逐字显示模型输出，证明事件间重绘生效。

### 8.4 端到端错误显示

最后一条任务（"Find all panic! macro invocations"）里模型发了一个非法工具调用（`arguments: null`）。修复前：TUI 静默卡住。修复后（v0.7.3 + v0.7.4）：

```
[tool call] grep
────────────────────────────────────────────────────────────
[tool error]
  invalid arguments: invalid type: null, expected struct GrepArgs
[error] agent stream error: provider error: api error (400): request failed: 400 Bad Request
```

错误链完整从 tool 层（参数错误）→ agent 层（流错误）显示给用户。**这正是 v0.7.3 Bug #2 修复的核心价值**。

## 9. 整体结论

v0.7.2 → v0.7.4 patch chain (commits `f167ac5` + `8c7be21`) 解决了 UX 测试中发现的 **全部 7 个问题**：

| 类别 | 数量 | 修复 commit |
|---|---|---|
| 🔴 Critical（功能完全不可用） | 2 | `f167ac5` |
| 🟠 High（严重但可恢复） | 2 | `f167ac5` |
| 🟡 Medium（影响体验） | 3 | `8c7be21` |

测试数：v0.7.2 的 676 → v0.7.4 的 689（+13 tests）。所有 689 个测试通过。

**核心结论**: nini 的 agent loop 架构已经 Pi 100% 等价（v0.7.2），但 TUI 层的端到端细节有 7 处需要修——端到端 UX 测试是发现这些的唯一方法。建议：
1. **下次每个 release 前都跑一遍真实 LLM 测试**（不只是 fixture）
2. **添加 `NINI_PROVIDER=http://...` 自检工具**——能验证 URL 约定等 provider 集成细节
3. **`<think>` 标签剥离应该做成 configurable**——有些用户可能想看 reasoning
