# nini 功能地图（用户视角 · Quality Left-Shift 运行时验证输入）

**0. 基线事实**

nini = Pi 的 clean-room Rust 重写（v1.0.1，源码 `/home/jin/nini`）。

能力基线：

- agent loop 单层折叠（MAX_TOOL_ITERATIONS=50、DEFAULT_MAX_PARALLEL_TOOLS=8、max_tokens=8192）；
- 内置工具 bash/read/write/edit/grep/find + 变更写保护 mutation_queue（并发写串行化）；
- 会话 JSONL 原子写 + 坏行跳过；
- 自动压缩（阈值压缩 + 溢出压缩，本地确定性摘要）；
- 截断容错（连续截断上限 + 接住半截继续 + 72h 兜底）；
- 信任闸（会话级 allow/deny）；
- 钩子面（M1 上下文钩子，M2 预留 before/after execute）；
- 多 provider fallback（5xx/429 退避重试）。

已知缺口：

- 无 subagent；
- 无后台/定时器；
- 无 extension 运行时；
- 无危险命令硬闸。

**1. 颗粒度**

按三级由粗到细划分，作为功能地图的粒度分层（用于设计与运行时验证）：

- 粗粒度（按用户路径）：描述「谁在什么场景下一步做什么」，即整体功能路径。用于发版整体核对。
- 中粒度（按业务状态）：描述「同一操作在不同业务状态下的分支行为」。用于运行时验证。
- 细粒度（按边界条件）：描述「触发不变量/异常临界的行为」。细粒度只用于验证。

划分原则：先粗后细；粗粒度用于发版整体核对，细粒度只用于运行时验证（功能级可执行用例）。

**2. 功能地图条目**

条目固定四要素：功能目标 / 触发操作 / 验证步骤 / 要验证的不变量。
条目按颗粒度分三层组织；条目基线为 F1–F10（固定，不增删改语义）。

### 2.1 粗粒度（按用户路径）

**F1 多 provider 调用与限流兜底**

- 功能目标：provider 调用中遇到限流类失败（5xx/429）时，按既定退避重试策略回退到下一个可用 provider，保证会话可继续，不出现无限等待或直接失败。
- 触发操作：一次会话中发起 LLM 调用，触发多 provider 回退（5xx/429 类失败）。
- 验证步骤：构造/触发 5xx 与 429 类失败场景，观察是否走退避重试并按既定策略回退到下一个 provider，记录重试次数与退避节奏。
- 要验证的不变量：provider 调用按既定策略重试（退避）并回退；无未定义的无限重试或直接失败行为。

**F2 Agent loop（LLM + 工具批次并发 ≤8、迭代上限、停止判断、follow-up）**

- 功能目标：agent loop 以单层折叠方式运行（LLM 调用 + 工具批次），工具批次并发不超过上限、迭代有上限、有停止判断，并支持后续 follow-up 轮次。
- 触发操作：用户发起一次 agent 会话，会话内每一次 LLM 调用与工具批次执行。
- 验证步骤：以一次完整会话运行触发工具批次，核对并发工具批 ≤ DEFAULT_MAX_PARALLEL_TOOLS=8、工具迭代 ≤ MAX_TOOL_ITERATIONS=50、max_tokens=8192；再核对正常停止与后续 follow-up 轮次的行为。
- 要验证的不变量：并发工具批 ≤ 8、迭代 ≤ 50、max_tokens=8192 生效；停止判断正常（到上限终止或按正常流程结束），follow-up 轮次可继续。

**F3 内置工具执行 + 并发写保护（bash/read/write/edit/grep/find + mutation_queue）**

- 功能目标：bash/read/write/edit/grep/find 六个内置工具可执行；并发执行下的写操作由变更写保护 mutation_queue 串行化，避免相互覆盖。
- 触发操作：会话内并行执行工具，尤其是并发 write/edit 写操作。
- 验证步骤：分别验证六个内置工具可正常执行；构造并发写场景（多个写工具并行触发），观察写操作被串行化、无覆盖。
- 要验证的不变量：六个内置工具均可执行且语义符合各自定义；并发写由 mutation_queue 串行化，不存在并发写相互覆盖。

**F9 配置/模型/skills 读取**

- 功能目标：会话运行所需配置、模型与 skills 按约定来源读取，保证运行期配置、模型选择与技能加载可用。
- 触发操作：会话启动、模型选择与技能加载时读取配置、模型与 skills。
- 验证步骤：构造不同配置与模型/skills 来源，验证配置、模型与 skills 按约定来源读取且取值一致，并与已核实的 provider 模型回退能力衔接。
- 要验证的不变量：配置/模型/skills 按约定来源读取、取值一致；读取失败按既定失败口径处理，不产生未定义行为。

### 2.2 中粒度（按业务状态）

**F4 会话持久化（JSONL 原子写、坏行跳过、续跑）**

- 功能目标：会话以 JSONL 原子方式持久化，会话中断后可续跑；坏行不会导致会话中断。
- 触发操作：会话运行中发生中断/故障，或重新加载/续跑会话。
- 验证步骤：运行中触发会话中断/故障，检查会话 JSONL 的写入方式（原子写）；重新打开或续跑会话，验证能从断点继续。
- 要验证的不变量：会话 JSONL 为原子写（无半截文件）；坏行被跳过且不中断会话；续跑能从断点恢复，不丢失已完成的会话状态。

**F5 自动压缩（阈值压缩 + 溢出压缩）**

- 功能目标：会话内容超过压缩阈值或超出可承载范围时自动压缩，支持阈值压缩与溢出压缩两种路径，压缩使用本地确定性摘要，压缩后仍可续跑。
- 触发操作：会话上下文/内容达到压缩阈值，或超出可承载范围时触发压缩。
- 验证步骤：分别构造「达到压缩阈值」与「溢出」两种场景，观察按对应路径压缩；再验证同一输入产生的压缩摘要一致（本地确定性）。
- 要验证的不变量：达到阈值/溢出时按对应路径压缩；压缩摘要为本地确定性（同一输入摘要一致）；压缩后会话仍可续跑，不破坏续跑连续性。

**F7 信任闸（会话级 allow/deny）**

- 功能目标：会话级设置 allow/deny，按会话级信任口径允许或拦截操作。
- 触发操作：会话内请求某类操作，其允许/拒绝状态由会话级 allow/deny 设置决定。
- 验证步骤：构造 allow 与 deny 两种会话信任设置，分别验证被允许的操作放行、被拒绝的操作被拦截。
- 要验证的不变量：信任闸按会话级 allow/deny 执行：允许项通过、拒绝项被拦截；不跨会话误放行或误拦截。

**F8 钩子面（M1 上下文钩子，M2 预留 before/after execute）**

- 功能目标：提供钩子面；当前为 M1 上下文钩子，M2 的 before/after execute 钩子已有预留（Tool trait 预留）。
- 触发操作：会话运行中触发 M1 上下文钩子；后续启用 M2 时按预留钩子位触发 before/after execute。
- 验证步骤：验证 M1 上下文钩子可按上下文钩子语义触发；验证 M2 before/after execute 钩子位已预留（预留属已知状态，不要求已实现行为）。
- 要验证的不不变性：M1 上下文钩子按约定可触发；M2 before/after execute 钩子位已预留，可作为后续扩展点接入，不因未实现而阻塞运行时验证。

### 2.3 细粒度（按边界条件）

**F6 截断容错（连续截断上限、接住半截继续、72h 兜底）**

- 功能目标：输出被截断时能容错：存在连续截断上限，半截内容被接住后可继续，存在 72h 兜底，不因截断中断会话。
- 触发操作：产生被截断的输出（连续截断、半截内容），或接近 72h 兜底边界时触发容错。
- 验证步骤：分别触发连续截断、半截输出与 72h 兜底场景，观察行为符合容错规则。
- 要验证的不变量：连续截断达到上限后有既定处理；半截内容被接住并可继续（不丢失已产生内容）；72h 兜底在边界触发且行为按既定口径。

**F10 危险命令处理（已知缺口：仅 prompt 提示、无硬闸；边界/风险项，不作为通过项）**

- 功能目标：（已知缺口，不作为通过项）nini 目前对危险命令仅作 prompt 提示，没有危险命令硬闸。本条目只作为边界/风险项登记，不设通过标准。
- 触发操作：会话运行中执行危险命令。
- 验证步骤：仅做风险登记核对（确认当前为「仅 prompt 提示、无硬闸」的已知状态）；如后续引入危险命令硬闸，应作为新的通过项在运行时验证清单中单独登记，不并入既有通过项。
- 要验证的不变量：（风险登记不变量）当前危险命令无硬闸、仅 prompt 提示，该缺口明确登记为已知状态；运行时验证以「风险项 + 后续处置」记录，不虚构为已实现能力。
